# `cez mcp` — an MCP server on stdio for agents outside cezar

> Slug: `cez-mcp` · Status: accepted (2026-11-08)
> Issue: #1109 (this proposal).

## TLDR

`cez mcp` is a Model Context Protocol server on stdio. An agent that runs *outside* cezar
(Claude Code, Codex, OpenCode, an orchestrator) lists, starts, follows, answers, reviews and
pushes the tasks of a running cockpit. It is a client of `/api/v1`, like `cez task` and
`cez runs`: run state stays in the cockpit process, and the route handlers keep their policy.
No new dependency, no new route, no setting.

## Scope

- **In:** `cez mcp` over stdio — 13 tools, `--read-only`, cockpit discovery, the project a call
  targets, cancellation and progress.
- **Out:** an HTTP transport (`/api/v1/mcp`, the second half of #1109). It widens exposure (a
  network listener, auth) and needs its own opt-in and review; nothing here blocks it.
- **Out:** `afterSeq` on `GET /runs/:id/history`, task alerts, an `open_pr` tool, and PR/issue
  status (the agent has `gh`; an earlier draft's `get_pr_status` was dropped).

## Decision: no SDK

The MCP SDK would be a new server runtime dependency. `CODE_REVIEW.md` keeps that budget
closed and exhaustive (hono, @hono/node-server, yaml, zod, smol-toml, ws, proper-lockfile);
widening it is a review decision that needs a reason no in-tree option can meet. Here one
exists: a tools-only server is `initialize`, `ping`, `tools/list`, `tools/call`,
`notifications/cancelled` and `notifications/progress` over newline-delimited JSON-RPC 2.0 —
about 250 lines (`packages/cezar/src/mcp/jsonrpc.ts`). Schemas come from zod
(`z.toJSONSchema`), which the budget already has. Tests drive the server through a small
line-based client (`client.testkit.ts`), so they need no SDK either.

## Protocol

- Versions answered: `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`. A client asking
  for another gets the newest (lifecycle rule); dropping one of these is breaking.
- `capabilities: { tools: { listChanged: false } }` — the list never changes in a session.
- Batches (JSON arrays) are refused with -32600: 2025-06-18 removed them.
- A request reusing the id of one still in flight is refused with -32600; the first keeps its
  cancel.
- `notifications/cancelled` aborts the call's signal, which also aborts the call's HTTP
  requests; the call's answer is never sent. A cancelled write may already have landed (a task
  may exist) — the client should read before retrying.
- `notifications/progress` only when the call carried `_meta.progressToken` (`wait_for_tasks`
  reports each poll).
- `server/discover` (the 2026-07-28 revision's probe) answers -32601 (method not found).
  Checked: Claude Code 2.1.316 sends `server/discover` first, gets -32601 and falls back to
  `initialize` 2025-11-25. Codex 0.166.0, in a live test, sent `initialize` with 2025-06-18
  straight away (no probe).
- stdout carries JSON-RPC only (`console.log` goes to stderr). When the client closes stdin the
  server aborts what is in flight, waits for stdout to drain (at most 2 s), then exits 0.
- `cez mcp` is routed in `index.ts`, which loads the cockpit's module graph first: about 0.3 s
  to the `initialize` answer warm. A separate light bin entry can come later if that matters.

## Finding the cockpit

1. `--url`, else `CEZ_API_URL` (empty reads as unset).
2. Else the cockpit this user runs: its runtime record (`~/.cezar/runtime/cockpits/<slot>`,
   #1739), in `serve`'s own slot order (named instance, default installed service,
   interactive), taken once `/api/v1/health` verifies it. A live record that cannot be verified
   is a tool error asking for `--url`, never a guess.
3. Else one look at `DEFAULT_COCKPIT_URL` (`http://127.0.0.1:4321`), for a cockpit too old to
   publish a record. No port scan.

Discovery is lazy: the handshake never needs a cockpit, and a missing one is a readable tool
error. The address is kept until a request cannot connect, then found again — a cockpit
restarted on another port is reached on the next call (a read is retried once; a write never).

**Which project.** `--project`, else `CEZ_PROJECT_ID`, else the registered project holding the
working directory (deepest root wins; with `--url` too). When none holds it, reads use the
boot project and `start_task` without `projectId` refuses with the project list — unless the
cockpit serves only its boot project. When the registry cannot be read, reads use the boot
project (`default`) and `start_task` without `projectId` refuses. A task id is not followed
into another project: without `projectId`, a 404 says to pass it.

## Tools

Names are snake_case and use the cockpit's word *task*; routes stay `/runs`. Arguments are
camelCase. Every tool states all four hints; clients base auto-approval on them.

| Tool | Route | readOnly | destructive | idempotent | openWorld | `--read-only` |
| --- | --- | --- | --- | --- | --- | --- |
| `list_projects` | `GET /projects` | ✓ | – | ✓ | – | ✓ |
| `list_workflows` | `GET /workflows` | ✓ | – | ✓ | – | ✓ |
| `list_models` | `GET /models` | ✓ | – | ✓ | ✓ | ✓ |
| `list_tasks` | `GET /workspace/runs-index` | ✓ | – | ✓ | – | ✓ |
| `get_task` | `GET /runs/:id` | ✓ | – | ✓ | – | ✓ |
| `get_task_status` | `GET /runs/:id` | ✓ | – | ✓ | – | ✓ |
| `list_task_events` | `GET /runs/:id/history` | ✓ | – | ✓ | – | ✓ |
| `wait_for_tasks` | `GET /runs/:id`, polled | ✓ | – | ✓ | – | ✓ |
| `start_task` | `POST /runs` | – | – | – | ✓ | – |
| `cancel_task` | `POST /runs/:id/cancel` | – | ✓ | ✓ | – | – |
| `push_task_branch` | `POST /runs/:id/git/push` | – | – | ✓ | ✓ | – |
| `send_task_message` | `POST /runs/:id/messages` | – | – | – | ✓ | – |
| `review_task` | `POST /runs/:id/finish` or `/continue` | – | – | – | ✓ | – |

`--read-only` does not register the write tools at all. Guarantees: `push_task_branch` never
force-pushes; `send_task_message` reaches only `waiting`, `running` or `queued` and never
reopens a finished task; `review_task` `accept` only marks the task done (no merge, commit,
push or PR) and refuses a task working in place (`worktree: false`, not read-only), whose
finish may commit to the base branch (spec `2026-10-20-trunk-based-projects`).

`wait_for_tasks` holds a call at most 45 s (default 40): Codex cuts a tool call at 60 s.
Every answer stays under 40 000 characters (it travels as text and as `structuredContent`).

## Inside a cezar task

With `CEZ_TASK_ID` set, `cez mcp` is read-only whatever the flags, and its `instructions` send
sub-tasks to `cez task create`. A task's agent with `cez mcp` in the user's own MCP config would
otherwise start tasks past dispatch's brakes — four children in flight, a budget carved from the
parent (spec `2026-09-10-dispatch.md`; AGENTS.md cites run 3f7eaf02). An absent `CEZ_API_URL`
inside a task still means the cockpit withheld its address: `cez mcp` does not look for one.

## `list_task_events` without `afterSeq` on `/history`

`/history` pages backwards by cursor and has no "events after seq N". `afterSeq` is therefore
served by a bounded walk back from the tip: at most 5 older pages (100 items each). A page's
leading turn opener does not count as coverage (`pageEventSlice` puts it there). Past the walk
the answer says `gap: true` and hands `olderCursor`. A server-side `afterSeq` would remove the
walk; it is a possible small PR of its own, not part of this one.

## Backward compatibility

Recorded in `BACKWARD_COMPATIBILITY.md` § CLI: the command and flags, exit codes, the tool and
argument names, the hints, the `--read-only` set, the guarantees above, the discovery order,
the protocol versions, and the in-task policy. Adding a tool or an optional argument is not
breaking; renaming or removing one, a hint toward less safe, or moving a tool out of the
read-only set is.
