A Questions inbox, next to Approvals

One place for every question waiting on you, from managers (CEZ:ASK decision cards) and from tasks (ask cards, parked waiting). A question closes when it is answered, dismissed, replaced, retracted or its task ends. Counts only include live questions.

The mockups below are interactive and share one state. Answer, dismiss (with undo) or toggle “Older” on the desktop page, and the sidebar badge, page header and phone update together. That is the count-sync rule this design proposes.

01 Desktop: sidebar and Questions page

Questions lives in manager mode’s Workspace group, between Approvals and Jobs. Each source is one group. A card is the same AskForm the chat uses, so one-tap single choice, multi-select, Other… and Need more info all work as they do today.

04 How a question closes

The goal: the main list holds only questions that still need you. Proven-stale cards close themselves. Suspected-stale cards leave the main list and the counts but stay reachable. The agent confirms which ones are really handled. The server decides every state except Older, so every surface agrees on what is live.

06 Notes

A. Data model: where open questions live

  • Manager cards stay as they are: an assistant message with ask. They gain askClosed?: { reason: 'dismissed'|'replaced'|'retracted', at, replacedBy?, note? }. The rule openAsk (engine.ts) becomes ask && askAnswer === undefined && askClosed === undefined. pendingQuestions follows automatically.
  • Task asks are currently resolved on the client (“the next user message closes the card”). They become server state: a capped RunRecord.asks[] (last 10: requestId, askedAt, questions, answeredAt?, closed?) in runs.json. A new ask.closed {requestId, reason, …} UiEvent is appended to the run’s NDJSON, so a replayed thread draws the quiet card. AGENT_PROTOCOL.md gains the event.
  • Read model: a workspace-level route, GET /api/v1/workspace/questions, returns { open[], closed[] }. Closed covers the last 7 days, capped at 50. Each item has a stable key (m:<managerId>:<messageId> or r:<projectId>:<runId>:<requestId>), its source, askedAt, the questions and its state. It is built from the manager engine plus the workspace dashboard’s cross-project run scan. Zod schemas go in packages/contract, and the route is chained into a family (single-mount).
  • Writes: answers reuse the existing routes (manager send with askId, run message). The only new write is POST /api/v1/workspace/questions/:key/dismiss. Undo is a client-side delay before the POST, so there is no reopen route and no wasted agent turn.
  • Older is a ui-state preference (questionsOlderAfterDays: absent = 7, 0 = off). It is never stored on a question.

B. Telling the agent: dismiss and close

  • Manager: the dismiss note is stored as a note message (shown in the chat as “You skipped «Design»”) and prepended to the next turn’s prompt. It does not start a turn by itself, so it adds no cost.
  • Task parked waiting on that ask: the note is delivered as the user’s message and wakes the run (one turn), the same as an answer. Otherwise the task would wait forever, which is the problem being fixed.
  • Task closed (idle or awaiting answer): dismiss closes the card and the badge but does not resume the session. The note is queued (queuedMessages) and goes out with the next Continue.
  • Task that already moved on (not waiting on this ask): the card is closed and no message is sent.
  • Replaced, retracted and ended send nothing. The agent caused the close, or no session is left.
  • The dispatch and manager prompts gain two lines: give each card an id, and use CEZ:ASK-CLOSE to withdraw a card.

C. Retraction mechanism (proposal)

CEZ:ASK-CLOSE design-v2 superseded by the v3 card
CEZ:ASK-CLOSE Release #2280 merged, moot
  • One marker line, parsed in the same place as CEZ:ASK (workflows/run.ts and the manager engine). It works the same for every runner and needs no tool permission.
  • The argument is the card’s optional id (already allowed in the CEZ:ASK JSON) or, as a fallback, a header in that chat or run. It only closes cards from the same source. An unknown id is ignored and leaves a warning event. The text after the id becomes the visible reason (max 140 characters).
  • Re-asking with the same id replaces the card (rule 1), so most agents never need the close marker.
  • cez-manager ask close <id> is not needed for v1. A manager ends its turn with text anyway, and the marker keeps one path for managers and tasks. It can be added later as a thin alias.

D. Counts stay in sync

  • One server function, liveQuestions(), counts open questions that are not Older. It feeds ManagerSummary.pendingQuestions, the Questions badge, the needs-you count, the desktop notch, native notifications and the phone push badge (RELAY_PROTOCOL badge count).
  • Live updates use one new WebSocket topic, questions, published only on change with { live, older }. Local mode subscribes once at the root, like health. Remote mode reconciles over SSE and refetches on run and manager events.
  • Closing a question re-sends the push badge, and on desktop it withdraws the matching OS notification where the platform allows it.
  • The sidebar text “Waiting for N answers” reads the same pendingQuestions, so it can no longer count obsolete cards.

E. Accessibility

  • Each source group is a <section aria-label>. Each card is a role="group" labelled by its question. Options are aria-pressed toggles, as in AskChoice.
  • Dismiss and answer announce through a polite live region (“Dismissed «Design». Undo available for 6 seconds.”). Undo is focusable and reachable with the keyboard before the timeout, and the timeout pauses while focus is inside the toast.
  • When a card leaves the open list, focus moves to the next card’s first option, or to the page heading if none is left. This is the same rule Approvals uses.
  • Closed and Older are disclosure buttons (aria-expanded). Reasons are text, never colour alone. Tap targets are 44px at pointer: coarse. Dark and light tokens are the cockpit’s own.
  • “Open in context” uses the existing #decision-<id> anchor and focuses the card, which flashes briefly unless reduced motion is on.

G. Relevance: proved, suspected, confirmed

  • Proved means the server closes the card itself, with no model call. That covers an expiry the agent gave (expires in CEZ:ASK), and linked work (PR, task or issue) reaching a final state, checked with the reference-state polling cezar already does for its chips.
  • Suspected means a probablyHandled: { why, since } mark on the question. It is computed from data the server already has: a later user message in that chat, later turns or commits on the task, later manager actions. It leaves the main list and the counts, and the card stays answerable.
  • Confirmed is the agent’s job. On each manager check and each task turn, cezar lists the agent’s open and probably-handled cards: “close what no longer needs the user: CEZ:ASK-CLOSE <id> <reason>”. Managers already get a snapshot at each check, so this adds a few lines, not a model call.
  • Late answers are guarded. Answering a probably-handled or Older card first asks “This may be out of date: <why>. Send anyway?” The answer that goes out says how old the question was and what changed since. Answering a closed card returns 409, as for an outdated merge, and the card redraws as closed.

F. Gating and scope

  • Task questions exist even when managers are off (CEZ_MANAGERS=0). In that case the Questions entry moves into the project sidebar’s Workspace group, and the route stays /questions (workspace-level).
  • No new CEZ_* flag. The page adds no network access and no timer, and Older is computed.
  • Phase 2 tests cover each close rule (replaced by id, by covered headers, partial overlap stays open, retracted, ended for done/cancelled/archived, idle-closed stays open), dismiss for each delivery path, undo, and count parity across summary, badge and push.
