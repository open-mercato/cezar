Deactivate a manager without deleting it

An inactive manager keeps its chat, memory, jobs, connectors and automation links, but runs nothing and makes no model calls until you switch it back on. Everything below is live: deactivate and reactivate managers from any mock (gear menu, sidebar row ⋯ or right-click, the phone's gear) and every other surface follows.

01Decisions

One recommendation per open question. The rule behind all of them: no model call happens without a click, and nothing the manager did not need a model for stops working.

02Desktop: sidebar and chat

Manager mode. Click a row to open its chat. Hover a row for ⋯, or right-click it. The gear in the chat header carries the same item, and the sidebar's Managers heading holds the bulk action.

localhost:4319/manager/ops

Inactive managers sort after active ones under a thin divider; the grey avatar carries a pause badge so colour is never the only cue. The Approvals count still includes their cards (answering costs nothing); Questions does not.

03Confirm dialogs

The deactivate confirm lists exactly what stops and what keeps going. The other three appear on reactivation, on sending to an inactive manager, and for the bulk action.

04Phone: manager index, CezarBot home, chat

The phone's manager index is also CezarBot's home. Tap a card to open its chat; the chat's gear opens a sheet with Deactivate / Reactivate.

05Questions and Approvals source blocks

The workspace pages group cards by source. An inactive manager's group keeps its cards, grey avatar and a flag; approvals stay one click; a question can be dismissed as is, or answered after reactivating.

06What stops, what keeps going

Stops (no model call, no process)
  • Watch checksThe timer is never armed for it: nextDue returns nothing, no snapshot is read.
  • Saved jobsListed and editable; they do not fire.
  • Follow-up turnsKept as notes for the next chat turn.
  • Chat turns, Check now, connector probes409 manager inactive unless the cockpit sends reactivate: true.
  • Account-reconnect restarts, crash recovery, usage-limit replaySkip inactive managers; deactivating clears a pending replay.
  • OS notifications and phone push for this manager
  • A turn in flightStopped as Stop does; its queue is cleared.
Keeps going (costs nothing)
  • Tasks it startedRun to the end; their cards post into its chat.
  • Automations linked to itRun on schedule; reports post into its chat.
  • ApprovalsDecided on the server; the manager hears the decision later.
  • Dismissing its questionsdismissAsk closes the card and leaves a note; no turn.
  • Everything it knowsChat, memory, jobs, cadence, connectors, settings: untouched, so reactivation restores them exactly.

07Data model and scheduler

One new optional field, one gate. An older cezar ignores the field (it survives its writes through mergeRow's extras) and would run the manager — acceptable for a downgrade.

// packages/contract/src/managers.ts — managerSchema
+ inactive: z.object({ since: z.string() }).optional(),   // absent = active; lives in managers.json, shared by every cockpit
+ activeSince: z.string().optional(),                      // written on reactivation: the floor for every due time

// routes (chained into the managers family, validated as middleware)
PATCH /api/v1/managers/:id        { active: boolean, catchUp?: boolean }
POST  /api/v1/managers/activity   { active: boolean }            // bulk; workspace-level, single-mount
POST  /api/v1/managers/:id/chat   { …, reactivate?: true }        // 409 "manager inactive" without it
// packages/cezar/src/managers/engine.ts
private enqueue(id, item) {
+  if (this.deps.store.get(id)?.inactive) return;        // THE gate: every model call goes through here
   …
}
private nextDue(manager, now) {
+  if (manager.inactive) return undefined;                // no timer is armed for it at all
+  const floor = msOf(manager.activeSince ?? manager.createdAt);
   jobs: max(lastRunAt ?? createdAt, floor) + everyMinutes   // no burst after a long sleep
}
reportTaskEvent:  inactive → the followUp:false branch (card + note, no scheduleFollowup, no alert)
reportAutomationRun: posts as today, no alert while inactive
pushWaitingTasks / alert / recover / authRetry replay: skip inactive
setActive(id, false): stop the active turn, clear queue + followup timers + resume, store inactive.since
setActive(id, true):  clear inactive, set activeSince + state.lastCheckAt = now,
                      post the "While inactive" summary (no model), catchUp → enqueue one forced watch

The summary counts what the chat file already holds since inactive.since (task-report and automation-report messages), plus skipped checks (⌊duration / cronMinutes⌋) and skipped job runs. No new state file.

Tests (phase 2)

  • Fake clock, an inactive manager with a cadence and two jobs, the clock moved past every due time: tick enqueues nothing and the runner factory is never called.
  • A followed task settles while inactive: the card posts, the note is kept, no follow-up turn, no OS notification.
  • Chat and Check now answer 409; chat with reactivate: true reactivates and runs exactly one turn.
  • Reactivate: no immediate turn without catchUp; exactly one forced watch with it; the next job fires at activeSince + everyMinutes.
  • Cockpit: grey avatar and pause badge, the confirm flows, the Questions badge excluding inactive managers' cards.
