# Task tags: a personal tag registry for tasks

Status: **draft 2026-11-23, awaiting owner review.**
Brief: `.ai/specs/briefs/2026-11-23-task-tags.md`.
Reverses one rejection in `2026-08-10-global-tasks-and-project-tags.md` (§ 3 below).

## TLDR

A user starts related tasks in batches (eight code reviews, five tasks on one feature) and today
can only find them again under Active or Archived. This spec adds **task tags**: a personal tag
registry in `~/.cezar/task-tags.json`, tags chosen in the composer, edited on any task in any
state, and a tag filter in the project task list and on the global `/tasks` page. A task stores
tag ids plus a name snapshot, so renaming a tag rewrites nothing and wiping `~/.cezar` still
shows the tags. Tags are a lens: cezar never routes, queues, limits or acts on them. Project
tags stay exactly as they are.

## 1. Problem

Every task surface groups tasks by project, by status, by workflow or by automation. None of
those says "these eight tasks are one batch". The owner already starts such batches by hand
and from inside a running task (`cez task create`), and other users want their own markers,
including a do-it-yourself status flow. A one-off "batch id" would cover only the first case,
so the mechanism is a general tag.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | A tag is an entity: `id`, `name`, optional `color`, optional `description`, scope (global or one project). | Rename and recolor without touching tasks. |
| D2 | Registry is its own file, `~/.cezar/task-tags.json`, via `taskTagsPath()` in `paths.ts`. Never a key in `config.json`. | Same argument as `agent-accounts.json`: a cezar that has never heard of tags cannot drop them. |
| D3 | A project-scoped tag stores the project's **realpath'd root**, not its slug. The wire speaks `projectId`, resolved against the registry on every read. | The `agent-accounts.ts` precedent: the root survives the registry being rebuilt. A tag whose root is no longer registered is inert, but it is listed in Settings so it can be deleted. |
| D4 | A run stores `tags?: { id, name, color? }[]`, the id plus a snapshot. The registry wins when the id resolves. A tombstoned id is hidden. An unknown id falls back to the snapshot. | Zero config: deleting `~/.cezar` degrades the display and never breaks it. |
| D5 | Several tags per task, at most 10. The UI is built for one tag. | Owner direction. |
| D6 | A name is unique, case-insensitively, among the tags **visible** in one project: that project's own tags plus all global tags. Typing an existing name reuses that tag. | Same reason as `normalizeProjectTags`: `API` and `api` must not split one group into two. |
| D7 | A tag created inline is **project-scoped** to the task's project. It can be promoted to global later. Demoting global to project is not offered. | Batches are almost always per project. Demotion would strand the tag on other projects' tasks outside its scope. |
| D8 | Edits to a task's tags are **deltas** (`add`, `remove`), never a whole-list replacement. | 2026-08-10's "lost tag": replacing a list from a stale cache silently deletes. |
| D9 | Delete writes a tombstone. Run records are never rewritten. | Rewriting every repo's `runs.json` is unbounded work across projects that may be offline. The tombstone stops the snapshot from bringing the tag back. |
| D10 | `+ Tag` chip in the composer's **main row**, after the Skill · workflow pill. It is not in the Options panel and is not remembered across tasks. | The Options panel is "remembered for <project>". A sticky tag would silently tag later, unrelated tasks. |
| D11 | Edits work on any status: queued, running, waiting, done, failed, archived. | A tag is metadata. It never touches the session. |
| D12 | Filters OR multiple selected tags and offer a "No tag" option, like the existing facets in `task-filters.ts` and the project-tags row. | Consistency. |
| D13 | No inheritance. Project tags are never applied to tasks, either as chips or when matching a filter. A dispatched child does not inherit its parent's tags. It gets tags only through `--tag`. | Owner direction. Implicit tagging is the engine acting on tags. |
| D14 | No new `CEZ_*` flag. | It adds no network, no process and no cost. Absent file = no tags, which is the old behavior. |

## 3. The reversal, stated

`2026-08-10-global-tasks-and-project-tags.md` rejected *"Tag runs instead of projects"* for two
reasons. Each still holds for the problem that spec solved. Neither holds for this one.

- *"Would have to be applied by hand to every task forever."* That spec wanted a stable
  relationship between repositories, so hand-tagging was a cost. Here the hand tagging **is**
  the feature: a batch is a deliberate choice the user makes, and an agent applies it in one
  flag (`cez task create --tag`). Project tags keep solving the repository problem unchanged.
- *"It has no home — run records live in each repo's `runs.json`."* Definitions now live in
  one place, `~/.cezar/task-tags.json`, and are edited there. A run holds only ids plus a
  snapshot (D4), so a rename never needs a cross-repo write. Its "lost tag" lesson is adopted as
  D8.

## 4. Data

### 4.1 Contract (`packages/contract/src/task-tags.ts`, new; re-exported from `index.ts`)

```ts
export const TASK_TAG_COLORS = ['gray','red','orange','amber','green','teal','blue','violet'] as const;
export const TASK_TAG_NAME_MAX = 40;
export const TASK_TAG_DESCRIPTION_MAX = 280;
export const RUN_TAGS_MAX = 10;
export const TASK_TAG_ID_RE = /^tt-[a-z0-9]{8,16}$/;

export const taskTagIdSchema = z.string().regex(TASK_TAG_ID_RE);
export const taskTagNameSchema = z.string().trim().min(1).max(TASK_TAG_NAME_MAX); // control chars rejected
export const taskTagColorSchema = z.enum(TASK_TAG_COLORS);

/** Wire shape. `projectId` absent = global. `orphaned` = scoped to a root no longer registered. */
export const taskTagSchema = z.object({
  id: taskTagIdSchema,
  name: z.string(),
  color: taskTagColorSchema.optional(),
  description: z.string().optional(),
  projectId: z.string().optional(),
  orphaned: z.literal(true).optional(),
  createdAt: z.string(),
  lastUsedAt: z.string().optional(),
});

/** On a run: id plus a display snapshot (D4). */
export const runTagSchema = z.object({ id: taskTagIdSchema, name: z.string(), color: taskTagColorSchema.optional() });

/** How a caller names a tag: a known id, or a name to reuse-or-create (D6/D7). */
export const taskTagRefSchema = z.union([z.object({ id: taskTagIdSchema }), z.object({ name: taskTagNameSchema })]);
```

Colors are a closed set of theme tokens, not hex, so a chip stays legible in light and dark. An
inline-created tag gets a color picked deterministically from its name's hash. The user can
change it later.

### 4.2 Registry file (`packages/cezar/src/workspace/task-tags.ts`, new)

```jsonc
{
  "version": 1,
  "tags": [{ "id": "tt-k3x9…", "name": "review batch 11-23", "color": "blue",
             "description": "…", "projectRoot": "/Users/…/repo", "createdAt": "…", "lastUsedAt": "…" }],
  "deleted": [{ "id": "tt-…", "deletedAt": "…" }]
}
```

House rules, copied from `agent-accounts.ts` and for the same reasons:

- Every field is `.catch`-defaulted and every object level is `.passthrough()`.
- Each `tags` and `deleted` row is salvaged on its own, so one bad row never evicts the rest.
- Writes go through one `mergeWriteTaskTags(fn)`: it resolves the path once, reads fresh,
  applies `fn` and writes atomically (`atomicWriteJsonSync`, `0600`). It is covered by
  `assertCezarHomeWriteIsSandboxed`.
- A corrupt or unreadable file degrades to empty with ONE warning. A read-only home makes write
  routes answer `503 { error }`, and reads still work.
- `deleted` is capped at 2,000 entries, with the oldest dropped first. A dropped tombstone can
  only bring a tag back as a snapshot chip, never as a registry entry.
- `lastUsedAt` is bumped whenever a tag is applied (on create or edit). The picker sorts by it.
- No migration. An absent file means no tags.

Exported helpers, shared by routes and tests: `listTaskTags(registry)`, `visibleTaskTags(projectRoot)`,
`resolveTagRefs(refs, projectRoot) → { tags: RunTag[] }` (reuses a visible name, creates a
project-scoped one otherwise, and refuses a tombstoned or out-of-scope id with a 400),
`createTaskTag`, `updateTaskTag`, `deleteTaskTag`.

### 4.3 Run record (`packages/contract/src/runs.ts`, `packages/cezar/src/runs/store.ts`)

- `tags?: runTagSchema[]` (max `RUN_TAGS_MAX`) on **both** run-record schemas: the contract's
  `runRecordSchema` and the store's own `runRecordSchema` (`runs/store.ts:177`). The store's
  schema is the one that parses `runs.json`, so missing it there drops the field on the next
  load. The field is optional, so old `runs.json` files still parse. It is omitted, not `[]`,
  when a run has no tags.
- `runIndexEntrySchema.tags?: runTagSchema[]`, so the global `/tasks` page and the palette can
  filter without the fat record. `dashboardTaskRowSchema` picks it up through `.omit`. Check
  `contract-parity` for both.
- Resolution happens **in the cockpit**, in one helper `resolveRunTags(run.tags, registry)`
  (`packages/web/src/lib/task-tags.ts`). The server keeps snapshots verbatim, which is the same
  "ship inputs, resolve in one place" choice the reference chips made in 2026-08-10.

## 5. API

Every shape below is a zod schema in the contract. Routes are chained into their family builder
and validated as middleware. All of them go into the BACKWARD_COMPATIBILITY.md §2 inventory.

**Workspace-level (single-mount, never `/p/`-prefixed):**

| Route | Body | Answer |
|---|---|---|
| `GET /api/v1/workspace/task-tags` | — | `{ tags: TaskTag[], deletedIds: string[] }` |
| `POST /api/v1/workspace/task-tags` | `{ name, color?, description?, projectId? }` | `201 { tag }`, or `409` on a name conflict (D6) |
| `PATCH /api/v1/workspace/task-tags/:tagId` | `{ name?, color?: Color\|null, description?: string\|null, global?: true }`, at least one key | `{ tag }`, `404` for unknown or deleted, `409` on a name conflict |
| `DELETE /api/v1/workspace/task-tags/:tagId` | — | `{ deleted: true }`. The tombstone is written. Deleting twice is idempotent. |

`PATCH` applies a field only when the body names it, the same per-key rule 2026-08-10 gave
`PATCH /projects/:id`. `global: true` checks D6 against every project before promoting.

**Project-scoped (both mounts; `route-parity.test.ts` covers the alias):**

| Route | Body | Answer |
|---|---|---|
| `POST /api/v1/p/:projectId/runs/:id/tags` | `{ add?: TaskTagRef[], remove?: string[] }`, at least one non-empty, `add` ≤ 10 | `{ tags: RunTag[] }`: the run's list after the change |

- The delta is applied inside one synchronous `store.updateRun`, so two concurrent edits compose.
  `add` of a tag already on the run refreshes its snapshot. `remove` of an absent id is a no-op.
  The result is capped at `RUN_TAGS_MAX`, and overflow is a `400` that changes nothing.
- Works on every status, archived included (D11). It never reaches the manager or the session.
- The change is published on the run's existing SSE stream, so other cockpit tabs update live.
- It is a separate route, not a `tags` key on `PATCH /runs/:id`, because `PATCH` there means
  "replace this value". A `tags` key on it would invite exactly the replacement D8 forbids.

**Creation inputs:** `createRunInputBaseSchema.tags?: TaskTagRef[]` (max 10), resolved through
`resolveTagRefs` before the run is created. A bad ref is a `400`, and no run is created. All ×N
variants get the same tags. The input reaches the deferred-start and automation create paths
through `createRunInputSchema` without extra code. Automations do not set it in this spec. The
dispatch create input (`packages/contract/src/dispatch.ts`) gains the same optional `tags`.

## 6. CLI (`packages/cezar/src/dispatch/task-cli.ts`)

```
cez task create "<objective>" … [--tag <name|id>]…
cez task tag [<run id>] [--add <name|id>]… [--remove <name|id>]…   default run: CEZ_TASK_ID
```

`--remove` by name resolves against the run's current tags. The command prints the resulting
tag names, one line. It uses the same three env vars and the same exit codes as the rest of
`cez task`. An agent may tag any run in its own project (`CEZ_PROJECT_ID`). That is no wider
than the trust it already has to create tasks there, and tags grant nothing. The dispatch prompt
(`dispatch/prompts.ts`) gains one line on `--tag` for batches. No human-facing `cezar tags`
command: management lives in Settings (§ 7.4). The new flags and subcommand are listed in
BACKWARD_COMPATIBILITY.md §1.

## 7. Cockpit

One query, `useTaskTags()`, reads `GET /workspace/task-tags` (staleTime 30s, invalidated by
every tag mutation). It also caches the run-tag edit mutation, which is **optimistic**: on
mutate it applies the delta to the cached run and the runs index, on success it replaces that
with the server's list, on error it rolls back, and on settle it invalidates. This is the fix
2026-08-10 gave `useUpdateProject`, built in from the start.

### 7.1 Tag picker (`packages/web/src/components/task-tag-picker.tsx`, new)

A popover in the same style as the Skill · workflow `source-pill`:

- a search field;
- this project's tags, then global tags, each group sorted by `lastUsedAt` and then by name;
- checked rows for tags already applied;
- when the typed text matches no visible tag (D6), a `Create "<text>"` row. It creates a
  project-scoped tag;
- a footer link, `Manage tags…`, to § 7.4.

Selecting or unselecting a tag sends one delta. The popover stays open for a second pick. It
works with the keyboard alone (arrows, Enter, Esc).

### 7.2 Composer (`routes/new-task.tsx`)

A dashed `+ Tag` chip right after `{sourcePill}` in the main row. Picked tags replace it with
colored chips (× removes) and a small `+`. Tags created there are real registry entries the
moment they are typed. The composer state is `tags: TaskTagRef[]`. It is held in the draft
(`new-task-draft.ts`), so a reload keeps it. It is **not** in `composerOptionsSummary` or the
remembered options. It is sent as `tags` on `POST /runs`.

### 7.3 Editing an existing task

- **Task header** (`routes/task-thread/run-header.tsx`): tag chips after the title, plus a `+`
  that opens the picker. The ⋯ menu gains `Tags…`, which opens the same picker.
- **Project task list** (`routes/tasks-overview.tsx`): the row shows its tag chips, collapsing
  to `+N` past two. `TaskQuickActions` gains a `Tag` icon button that opens the picker anchored
  to the row.

  Note: there is no right-click context menu on task rows today. The brief's "Tags… in the row
  context menu" lands as this quick action plus the header's ⋯ item. A new context-menu
  primitive is out of scope (see § 11, Q1).
- **Sidebar rows**: chips are not shown. The sidebar is a finder, and its width is spent on the
  title.

A chip whose tag is tombstoned is not rendered. A snapshot-only chip (unknown id) renders in
neutral color with the snapshot name. It can be removed and filtered by, but it cannot be edited.

### 7.4 Management (`settings/global` → new section `task-tags`)

A list grouped by scope (Global, then each project, then "Unregistered project" for orphans). Per
row: name (inline rename), color swatch menu, description, `Make global` (project tags only)
and Delete. Delete asks for confirmation and says the tag disappears from every task. No usage
counts: counting would mean reading every project's runs, and the global `/tasks` filter already
answers "what is tagged X". Registered in `settings-shell.tsx`'s nav.

### 7.5 Filters

- **Project task list**: `TaskTableFilters` gains `tags: readonly string[]` (ids, plus the
  `UNTAGGED` sentinel). `TaskFacetId` gains `'tags'`, and `filterTaskTable` and
  `taskFacetCounts` handle it. The facet is shown beside Active/Archived only when some loaded
  run has a tag. Options are the resolved tags present on loaded runs. Selection is OR (D12).
- **Global `/tasks`** (`routes/global-tasks.tsx`): a second facet row, **"Task tags"**, under the
  existing "Tags" row, which is renamed **"Project tags"** with unchanged behavior. It reads
  `runIndexEntry.tags` and matches a task's own tags only (D13). The two rows AND with each other,
  as every facet row does today.
- Filter state lives wherever the sibling facets keep theirs today. No new persistence.

## 8. What does not change

- Project tags: storage, `normalizeProjectTags`, `PATCH /projects/:id`, `cezar projects tag`
  and the Settings → Projects editor.
- Engine: scheduling, `maxParallel`, admission, dispatch, managers and automations never read
  `tags`.
- `.ai/cezar/.gitignore` maintenance: the new file is in `~/.cezar`, not the data dir.

## 9. Failure and degradation

| Situation | Behavior |
|---|---|
| `task-tags.json` missing | No tags in pickers, and runs show snapshot chips. Creating a tag recreates the file. |
| File corrupt | One warning, treated as empty, and the next write replaces it. |
| Home read-only | Reads work. Tag create, edit and delete answer `503`. Run-tag edits that only reference existing ids still work, because they write `runs.json`. |
| Tag deleted on one machine-local registry, run moved between machines | Snapshot chip (D4). |
| Project deregistered | Its tags turn `orphaned`. They are hidden from pickers and listed in Settings. |
| Old cezar reads a run with `tags` | Ignored. `runRecordSchema` strips unknown keys on parse, so an old version's rewrite **drops** them. This is acceptable: tags are a lens, and the BC note records it. |

The last row is a real downgrade loss. It is worth stating in BACKWARD_COMPATIBILITY.md §3
rather than engineering around it. Keeping the record parse lossless across versions is a
separate concern this spec does not take on.

## 10. Tests

- **`workspace/task-tags.test.ts`**:
  - per-row salvage, and a corrupt file degrading with one warning;
  - the tombstone cap;
  - D6 conflicts, covering project vs global, case-insensitivity and promotion;
  - `resolveTagRefs` for reuse, create, tombstoned id and out-of-scope id;
  - a sandboxed-home write guard.
- **Routes**:
  - contract parity for every new shape;
  - `typed-bodies` reachability;
  - `route-parity` for `/runs/:id/tags`;
  - `bc-route-inventory`;
  - concurrent deltas: two `add`s in flight both land, which is the regression test for D8. It
    must fail against a replace-list implementation, so prove it red first (AGENTS.md);
  - tagging an archived run and a running run;
  - `POST /runs` with a bad ref creating nothing.
- **Store**: an old `runs.json` without `tags` parses, and `tags` is omitted when empty.
- **CLI**: `cez task tag` add/remove by name and id, and the default run from `CEZ_TASK_ID`.
- **Cockpit**:
  - `resolveRunTags` for registry wins, tombstone hidden and unknown id shown as snapshot. This
    pins the empty-registry case;
  - picker ordering and the create row;
  - composer sends `tags` and does not remember them for the next task;
  - optimistic edit rollback;
  - `filterTaskTable` with `tags` and `UNTAGGED`;
  - the global page's two rows staying independent.
- **e2e smoke** (`packages/web/e2e/`): create a task with a new tag, filter the list by it,
  rename the tag in Settings, and see the new name on the task.

## 11. Open questions for the owner

1. **Row context menu.** No right-click menu exists on task rows. This spec puts `Tag` in the
   row's quick actions plus `Tags…` in the header's ⋯ menu (§ 7.3). Is that enough, or should a
   row context menu be added (and to the sidebar too)?
2. **Inline-create scope** (D7). Should a tag created inline default to project-scoped? The
   alternative is a picker row that offers both "in <project>" and "global".
3. **Bulk tagging from the selection toolbar** (`TasksSelectionToolbar`). It is left out: batch
   tagging is done at creation or through the API. It would be a small follow-up that loops the
   per-run route.
