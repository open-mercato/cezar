Add an agent account from the cockpit

Click Add account, pick an agent and sign in. cezar makes a private folder for the account and runs the agent's own login in it. You see the link and any code, paste the code back if the vendor asks for one, and the account is ready, with its identity and plan shown. It works the same on a phone through the relay. 1 · Today

Settings → Agent accounts → Add account asks for a config folder. The folder has to be signed in from a terminal (CLAUDE_CONFIG_DIR=~/.claude-work claude), either before or through Connect. A paired phone gets no accounts at all (accountsEnabled() refuses relay scope, because folder paths reveal the host's layout). The sign-in UI itself already exists. The reconnect card (#2314) runs the vendor's login headless and shows a browser tab, a device code, a paste-code field or a terminal hand-off. This design reuses that body. What it adds is the account creation around it.

Directory layout

~/.cezar/                      (cezarHomeDir(); CEZ_HOME relocates it)
  agent-accounts.json          rows gain optional  managed: true, pending: true
  agent-homes/                 0700
    claude/work/               0700  CLAUDE_CONFIG_DIR for account "work"
    codex/client-acme/         0700  CODEX_HOME
    kimi/second/               0700  KIMI_CODE_HOME

managed means cezar made the folder and may delete it. pending means no sign-in has been confirmed yet, so pickers, fallback candidates and selections skip the row. Both survive an older cezar through .passthrough(). An older cezar shows a pending row as an ordinary account, which is harmless.

API (chained into the agent-profiles family, every shape in packages/contract)

CallWhat changes
POST /workspace/agent-profilesNew body variant {provider, label, managed: true} with no configDir. The server allocates the id and folder and writes pending: true. The old body is unchanged.
POST /providers/login {provider, profileId}Unchanged. On a confirmed sign-in, LoginSessionManager.connect clears pending through a new dep, markSignedIn, so the row turns usable even if the cockpit was closed.
DELETE /workspace/agent-profiles/:idManaged rows only: runs the CLI's own logout under the account's env (best-effort, 15 s timeout), then rm -rf the folder after a realpath check proves it's inside agent-homes/. Unmanaged rows behave as today: the folder stays.
Cancel in step 2DELETE /providers/login/:sid, then the DELETE above
Boot sweepA pending managed row older than 24 hours with no live session is removed along with its folder.

Phone and hosted

  • Paired phone (relay scope) gets a narrowed allowance: the listing without configDir or files, POST only with managed: true (a client path is still refused), and DELETE only for managed rows. The phone never sends or receives a host path. The login session already strips a named account's command for phones (phoneSafeSession).
  • Links open in the system browser. Both shells hand a window.open off to the OS (ServerActivity.onCreateWindow, iOS createWebViewWith), so the vendor page opens in Safari or Chrome. The user copies the code there, switches back, and pastes it.
  • Hosted web: same gate as today. The family needs CEZ_REMOTE_AGENT_ACCOUNTS=1, and without it step 1 shows the refusal.

Security

  • Tokens stay in the vendor CLI's own store. The page receives only the phase, an allow-listed URL, a device code, an expiry and a fixed reason.
  • A pasted code or key goes from an uncontrolled <input type=password> straight to the route and on to the CLI's stdin. It never enters React state, the query cache, the run store, logs or telemetry. Over the relay it travels inside the paired Noise tunnel, the same protection every other request gets, and nothing extra.
  • The folder is 0700, and deletion is limited to agent-homes/ by realpath. A hand-edited configDir can't make cezar delete anything else.
  • Cancel, expiry or failure on a new account kills the login's process group (as today), then deletes the pending row and its folder, so nothing half-signed is left behind.
  • CEZ_DRY_RUN=1 runs the mock login session in a real managed folder under the sandboxed home.

Tests

  • Server: managed create (id, folder, mode, pending), the relay-scope listing has no paths, a phone can't send configDir, delete refuses outside agent-homes/ (symlink case included), pending is cleared on connect, the boot sweep, and cancel cleanup. Contract parity and route inventory cover the new body.
  • Web: the wizard's states (pick, each signing method, success with identity, duplicate login, expired, cancel confirm), the Advanced folder path, hiding pending rows in pickers, and the phone sheet layout.

6 · Recommendation & decisions

Recommendation: variant A. A three-step dialog from Settings → Agent accounts, the same component as a full-height sheet on a phone, managed folders by default, and the folder path moved behind Advanced. It reuses the reconnect card's signing body without changes, so the two flows can't drift apart.
