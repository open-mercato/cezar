# Global tasks page + project tags (grouping connected repositories)

## TLDR
The cockpit can show one project's tasks at a time. Real work does not stop at a repo boundary: a storefront is an API, a web app and a design system, and "how is the storefront doing?" currently means visiting three sidebar groups and holding the answer in your head. This spec adds (a) free-form **tags** on a registry project — labels that say *these repos are one piece of work* — and (b) a **global Tasks page** at `/tasks` that lists every registered project's runs in one table, filterable by tag, status and workflow, groupable by any of those plus project, with each row carrying its PR/issue chip and an archive action. Tags are an optional field on the existing project registry entry, so nothing migrates and a workspace that never tags anything behaves exactly as before.

## Problem Statement
Every task surface in the cockpit is project-scoped by construction. `/p/:projectId/` is the tasks table, `useRuns()` is the active scope's run list, and the sidebar renders one collapsible group per project (`components/project-groups.tsx`). The only cross-project surface that exists is the ⌘K palette, which reads `GET /api/v1/workspace/runs-index` — and it is a *finder*: it answers "where is the task called X?", not "what is happening across these four repos?".

Two concrete gaps follow:

1. **No cross-project view at all.** With eight registered projects, "which tasks need me right now?" is eight sidebar groups, each with its own attention badge. The badges are per project; nothing sums or lists them together.
2. **No way to say which repos belong together.** Even if a cross-project list existed, a workspace is not a flat list of equals — some repos are one product, others are unrelated. cezar holds no fact that expresses that relationship, so any global list would be an undifferentiated pile.

The two gaps are one feature: a global list is only useful if it can be sliced by the grouping the user actually thinks in, and a grouping is only useful if something reads it.

## Proposed Solution
**Tags on the project registry entry.** One optional `tags: string[]` on `workspaceProjectSchema`, edited in **Settings → Projects** (a token field per row) and over ssh with `cezar projects tag <id> [<tag>…]`. Free-form, normalized on write (trimmed, deduped case-insensitively, sorted, bounded), and **omitted rather than `[]`** when a project has none — the same "absent = inherit/none" doctrine `maxParallel` follows.

**A global Tasks page at `/tasks`**, outside `/p/:projectId` for the same reason `/settings/global` is: "all projects" scoped to one project is a contradiction. It reads the existing workspace-level `GET /api/v1/workspace/runs-index` — one request for the whole registry — joins it to `GET /api/v1/projects` for names and tags, and renders a filterable table.

**Picking a project LEAVES for it.** There is no project filter; every project name links to that project's own Tasks page. See the Architecture note — the local page is a strictly better answer to "just this project" than the global one could be.

**A task's tags are its project's tags.** Tags label repositories, not runs. That is what makes one tag reach three repos, and it means grouping by tag FANS OUT: a task in a repo tagged `storefront` + `frontend` appears under both, because it genuinely belongs to both.

**Alternatives considered and rejected:**

- *Tag runs instead of projects.* Rejected: the useful relationship is between repositories and it is stable, while a per-run label would have to be applied by hand to every task forever. It also has no home — run records live in each repo's `.ai/cezar/runs.json`, so a cross-repo grouping stored there could never be edited in one place.
- *Fetch N per-project run lists on the global page.* Rejected: `GET /runs` answers full `RunRecord`s (`steps[]`, `workflowDef`), so a forty-project workspace would ship megabytes to paint a title and a dot. The slim index already exists for exactly this reason.
- *Make tags a first-class concept the engine reads* (routing, shared queues, per-tag concurrency). Rejected as scope and as design: a tag is a **lens**. The moment it also grants or restricts something, removing one becomes dangerous, and the cheap "just tag it and see" gesture this feature depends on is gone.
- *Put the global page under `/p/<boot>/tasks`.* Rejected: it would inherit a project scope it must not have, and its data (the workspace index) has no scoped spelling.

## Architecture

**1. Contract (`packages/contract/src/projects.ts`, `runs.ts`).**

```ts
// projectListEntrySchema
tags: z.array(z.string()).optional(),

// updateProjectInputSchema — every key optional, at least one required
{ maxParallel?: number|null, tags?: string[]|null }
```

`PATCH /api/v1/projects/:projectId` becomes **per-key**: a field applies only when the body names it. That is what keeps the pre-tags `{ maxParallel }` body meaning exactly what it always did, and what stops the tags editor from clearing a concurrency ceiling. An empty body is still refused (a `.refine`), as it was before tags existed — a request naming no field is a mistake, and answering 200 to it would report a change that never happened.

`runIndexEntrySchema` grows `workflow` (required — every record has one), `branch?`, `startedAt?`, and the six inputs `taskReference()` reads (`pullRequestUrl?`, `referencedPullRequestUrl?`, `prNumber?`, `issueNumber?`, `referencedIssueUrl?`, `markerRefs?`): the columns the global table paints. Deliberately NOT `steps[]`/`workflowDef`, which is the whole reason the slim row exists.

A task has **several** references, not one: opened on issue #524, ABOUT PR #530, having created PR #533 — all true at once. `taskReferences()` returns them all, strongest first, built by walking an ordered list of SOURCES so a further kind is one entry rather than a rewritten winner-picking chain; `taskReference()` is now simply its head, so every existing single-slot surface (the sidebar row, the per-project table) answers exactly what it always answered. The PR half of that list is `prUrls()`, which `taskPrUrl()` also takes its head from — one place for #407 and #526, so the singular and plural accessors cannot drift on them. The global table paints up to two chips — what fits one line, and the common case (a task's own PR plus the issue it came from) — and collapses any remainder into a `+N` that opens a popover of every reference as a real link. A tooltip was the first attempt and was worse than saying nothing: it told the reader the references existed and then refused to let them go there. The popover lists ALL of them, not just the hidden ones, because at the moment you open it the question is "what does this task point at?" and answering with the leftovers makes you reassemble the set from two places. Its rows are `ReferenceChip`s, so the http-only guard, the accessible names and the `target`/`rel` handling are the same ones every other reference link uses. It opens on **hover** where hovering exists and on **click** everywhere — touch and keyboard included. Radix's `HoverCard` would have given the first for free but neither of the others (it is explicitly not a touch affordance), so this is a `Popover` — click-and-keyboard by construction — with hover layered on: `pointerenter`/`pointerleave` on both the trigger and the content, a close delay so the gap between them is traversable, and `pointerType !== 'touch'` so the `pointerenter` a TAP fires does not open the list under the finger only for the following click to toggle it shut. How it opened also decides focus: a click hands the keyboard the links, a hover must not yank focus out of whatever the reader was doing.

**Every reference is a link, including the ones known only by number.** A run often carries `prNumber`/`issueNumber` with no URL ever scraped, and a chip that says `#5127` and cannot be clicked is a dead end. A project-scoped view can synthesize the URL from the one repo it stands in; this page has a different repo per row, so `projectListEntrySchema` grew `repoUrl` — the remote's web root, rebuilt server-side from the PARSED remote (never string-edited from the raw one, which may carry credentials) and free because the registry probe already parses it for `forge`. `taskReferences(run, repoBase)` then synthesizes under the same hard limit `taskIssueUrl` already obeyed: only ever the project's own repo, never a transcript-scraped URL (#526), and a real URL always beats a synthesized one — a task's PR can legitimately live in a fork. Without a `repoBase` the chip stays inert text, because a link that goes somewhere invented is worse than one that is absent. Transcript candidate lists (`referencedPrCandidates`) stay unread — they routinely name other repositories (#526), so a further reference must arrive as a real field.

The reference inputs ride **verbatim** rather than pre-resolved into a `{kind, number, url}` server-side. The rule that picks between them is subtle — #407 (a run that *reviewed* a PR must not claim it as its own) and #526 (an issue-subject run must not adopt an incidental transcript PR) — and it already exists, tested, in the cockpit. A second resolution on the server would be a second rule, and the two would drift; `taskPrUrl`/`taskIssueUrl`/`taskReference` were widened from `RunRecord` to a `TaskReferenceInput` `Pick` instead, exactly as `runTitle` and `deriveAttention` already were, so all surfaces answer identically.

Note `workflow` here is the raw name — the display refinement `workflowLabel()` needs `steps[]` to resolve a `(planned)` chain to its first agent, so a `(planned)` run reads as itself on this page.

**2. Registry (`packages/cezar/src/workspace/config.ts`, `projects.ts`).** One optional field on `workspaceProjectSchema`, bounds imported from the contract so a value the PATCH route accepts can never be degraded away by the next load's `.catch`. Normalization is one exported function, `normalizeProjectTags`, shared by the route and the CLI:

- trim, drop empties, truncate over-long, cap the list;
- **dedupe case-insensitively, first spelling wins** — this is the load-bearing rule. Tags exist to be a grouping key, and `API` beside `api` splitting one group in two is the exact failure the feature would otherwise ship with;
- sort, so two projects tagged with the same set store and render the same list;
- return `undefined`, never `[]`, so an untagged project stores no key.

**3. Server (`server.ts`).** The PATCH handler applies each key only when present, normalizing tags on the way in. `runIndexEntry` spreads every new optional key conditionally (the `JSON.stringify`-drops-undefined rule the parity guard fails on) and `workflow` unconditionally. The route's body schema is the CONTRACT's, imported rather than restated.

**3b. Convergence is a UI problem, not only a normalization one.** The normalizer can dedupe within ONE project's list; nothing in it stops the next project from inventing `store-front` beside `storefront`, and a group that exists in one repo only is not a group. So the Settings token field **autocompletes from the workspace's whole vocabulary** (`lib/project-tags.ts`: `allProjectTags` + `suggestTags`), offering everything on focus — "which tags exist here?" is the first question someone tagging a second repo has — filtering as you type, prefix matches first, hiding tags the project already carries and hiding an exact match (the field's own Enter already commits that). Anything not on the list is still simply typed, so the vocabulary guides without gating.

The list is a Radix popover anchored to the input rather than an in-flow dropdown, because the registry table sits inside `overflow-x-auto` and would clip one. **This component owns dismissal, not the layer** (`onInteractOutside` prevented; closing happens on the input's own blur, Escape, Tab and picking). That is not a preference: the list opens on the input's `focus`, so Radix's `DismissableLayer` mounts *during that focus dispatch* and its freshly-added document listeners see the very focus that opened it as an interaction outside itself — the list appeared for a blink and vanished on every click. Radix cannot tell those apart here, because the focused element is deliberately outside the layer: this is an anchored listbox, not a popover you move into. Blur is a sound substitute precisely because suggestions commit on `mousedown` with the default prevented, so picking one never moves focus. The pane itself widened from `max-w-2xl` to `max-w-4xl` and the table took explicit `<colgroup>` widths: it is the one settings section whose content is a six-column table rather than a stack of form fields, and auto-layout gave the Tags cell whatever the fixed-size controls left over — which was not enough for a single `open-mercato` chip without breaking it across two lines. Focus never leaves the input (`onOpenAutoFocus` prevented, suggestions committed on `mousedown`), and the input carries the `combobox`/`aria-activedescendant` wiring by hand since the listbox is a portalled sibling rather than a child.

**4. Cockpit.** `routes/global-tasks.tsx` is markup + local filter state; everything decidable is in `lib/global-tasks.ts` (join, facets, filter, group), tested as a table. `components/facet-filter.tsx` holds the three reusable controls — a searchable multi-select popover pill, a toggle chip, a segmented control.

Facets are **sets**, not single values: values OR inside one facet and AND across facets, so *"anything running or waiting in storefront or infra"* is one set of clicks rather than four separate questions. Each option carries how many rows it would leave, counted against the list as the OTHER facets narrow it — so a filter that would empty the table says so before it is clicked, and unticking a value promises a number it can actually deliver.

There is deliberately **no project facet**. Narrowing this page to one project is that project's own Tasks page, which is a strictly better version of the same answer: live SSE instead of a poll, the full column set, the composer, no per-project cap on the list. So every project name here — the row's cell and the group heading — is a **link out**, not a filter. A project filter would have offered a worse local view from inside the global one and quietly competed with the page it should be handing off to.

**Group-by is a toggle row, not a radio row.** Pressing the pressed grouping releases it, so there is no `None` button: "not grouped" is the absence of a grouping, not a fifth one, and a row of toggles where one is always pressed claims grouping is mandatory when it is not. `SegmentedControl` therefore takes `value` as a plain string (a value matching no option means nothing is pressed) and reports a click on the already-pressed option rather than swallowing it — the caller decides what a re-click means.

**Read / unread** is per row too, an open eye to stamp the receipt and a closed one to take it back (#775). It appears only where a read state exists — `canBeUnread`, the same decider behind the unread dot — so a running task offers no button rather than one that does nothing. The icon shows the ACTION, not the state; the state is already visible as the violet dot beside the title. Both row actions go through one `useIndexedRunMutation`: act on the run in ITS OWN project (explicit id, because `queryScope()` here answers with the boot project), patch the workspace index optimistically (the project's own run list may not even be loaded), reconcile on settle, roll back with the server's reason on refusal.

**Task is the only column with no width, and everything else is pinned as narrow as its content allows** — Task grows on exactly what the others give up. That is also why the row paints only the STRONGEST reference (the `+N` opens on hover and lists the rest, so folding them costs a pointer-move rather than information) and why Tags moved to the `xl` breakpoint: a cross-project list is scanned by title, and every other column answers a question you ask about a row you have already found.

**There is no Branch column.** A cross-project list is read by title, and the width is worth more to the one column that has no fixed size than to a value most rows repeat. Branch stays SEARCHABLE though — pasting a branch name from a terminal to find the task that made it is a deliberate gesture, and the per-project table already makes exactly this exception: its Branch column is folded by default while `filterRuns` searches it anyway.

**Cost, CPU and memory** are columns too, reading the same live/peak rule as the per-project table (`usageCells`, widened to a `Pick` like `runTitle` and `deriveAttention` before it): a live sample emphasized, a finished run's persisted peak dimmed and labelled, an honest em dash otherwise. The live sample rides the index ROW (`usage`, attached server-side exactly as `GET /runs` does) rather than the run event stream, because that stream is project-scoped and a page showing forty projects cannot open forty of them — and it can ride a workspace-level answer at all only because the sampler is process-wide: one cezar process runs every project's agents. Cost obeys the host's `CEZ_HIDE_COST` gate via `usageMetricVisibility`, since a cross-project view is not an exception to it.

**Archiving** is per row (`POST /p/<projectId>/runs/<id>/archive`, through an explicit-project client function for the same reason the links are explicit). Not the per-project table's count-gated "Archive finished" broom: a sweep that crossed repository boundaries would be one click firing N writes into N repos, and "finished" is a judgement each project's own page is better placed to make. The button only appears on a run that is genuinely finished (or already archived), so it never invites the question of whether it also cancels.

**5. Navigation.** An "All tasks" row above the sidebar's project groups (multi-project workspaces only — with one project the page is that project's own table under another name), a ⌘K Views row, and `/tasks` in the page-title map. Both links are PLAIN router links: the scope-aware `Link` would prefix the target with the active `/p/<id>`, which is not a route.

**Two bugs this surfaced.**

*The stale read receipt.* Opening an unread task from `/tasks` and coming straight back showed it still unread until a refresh. The receipt mutations (`useMarkRunSeen`/`useMarkRunUnseen`) patch the project-scoped run list and detail; the index is a third, independent cache with a 30s staleTime that nothing re-read. Fixed by invalidating `workspaceQueryKeys.runsIndex` on success. Invalidate rather than patch, deliberately: patching needs the run's project id (the index keys on `projectId + id`), and these hooks know a run only by id — deriving the project from the router would couple a data hook to a `<Router>` its own unit tests do not provide. Nothing observes the index from inside a thread, so this costs no request; it means the page's next mount reads the truth.

*The lost tag.* Adding two tags in a row dropped the first. The editors are bound to the server value with no local mirror, so between the PATCH and the refetch the cached project still held the OLD list — and because a tags PATCH replaces the list wholesale, a stale read is a silent DELETION rather than a stale display. `useUpdateProject` is now optimistic (write the patched entry into the projects cache on mutate, replace it with the server's normalized answer on success, roll back on error, invalidate on settle), which closes the window so the second click composes on top of the first. `maxParallel` gets the same protection for free.

*The phantom selection.* `ProjectGroups` resolved its active project as `pathnameProjectId(pathname) ?? bootProjectId`, so on any page belonging to NO project — `/tasks`, and `/settings/global` before it — the boot project was painted as selected. Fixed by splitting the two questions that fallback was conflating: `scopedProjectId` (null off a `/p/` path) decides what is HIGHLIGHTED, `collapseAnchorId` (still falling back to boot) decides which group is OPEN by default, so landing on a global page neither lies about the selection nor folds the sidebar shut.

## Constraints and trade-offs

- **The index is capped** at `RUNS_INDEX_PER_PROJECT` (200) per project. The page renders the `truncated[]` the endpoint already returns, naming the projects it bit — a capped list that says nothing reads as "your task is not here" when the honest answer is "not in the newest 200".
- **No live stream.** Run SSE is per-project; a page showing forty projects cannot open forty streams. The page polls the index every 15s — an opt-in argument to `useRunsIndex` that only this caller passes, so the palette keeps its 30s staleness and the cockpit's no-polling default stands everywhere it has a stream to rely on.
- **No cross-project bulk actions.** Archive is one row at a time; there is no global "archive finished" and no multi-select. A sweep across repositories is a lot of writes behind one click, in projects the user is not looking at.
- **Filters, grouping and the Active/Archived split are URL state** (`?q=&tag=&untagged=&status=&workflow=&group=&archived=`), so a filtered view survives a refresh, pastes into a chat and sits in a bookmark. The URL IS the state rather than a mirror of it — no second copy to drift — and every write is a `replace`, so Back leaves the page instead of undoing one chip at a time. Empty facets emit no key, so an unfiltered page stays a bare `/tasks` and "is anything filtered?" is visible in the address bar. The decoder is deliberately forgiving (an unknown `group` is "not grouped", empty values are dropped): it parses whatever a pasted or hand-edited URL carries rather than failing on it. The untagged bucket rides its own `untagged=1` flag, because its sentinel is `' untagged'` — as a `tag` value it would either serialize confusingly or, spelled without the space, collide with a repo genuinely tagged `untagged`.

  The search box is the one control that writes on a delay: every other one is a discrete click, but a text field writing per keystroke means a `history.replaceState` per keystroke, which browsers rate-limit (Safari drops calls past ~100 in 30s). It types into local state and flushes after 250 ms, with a guard so a flush landing mid-word cannot overwrite characters typed since.

  The **Active/Archived split is `archived=1`, present-or-absent**, rather than `view=active|archived`: Active is the default and the overwhelmingly common case, so spelling it out would put a key in every shared link that says only "the normal thing". Defaults emitting nothing is the same rule the facets follow.

  It still reaches the shared `useListView()` context — the thing that keeps this page, the per-project table and the sidebar quick-list answering one question — but ONE WAY: here the URL is the authority and the context follows it. Nothing else on this route can change the view (the multi-project sidebar's groups only read it), so there is no loop to break, and walking from an archived view into a project keeps the same question in force.
- **A run whose project has left the registry still renders**, showing its raw project id and grouping as untagged. Dropping a task from the list because the registry response is a few seconds staler than the index would be the worse failure.

## Backward compatibility
Additive throughout, per BACKWARD_COMPATIBILITY.md §1, §2 and §9:

- `tags?` is a new optional key on the projects GET shape and on `config.json`'s `projects[]`. An old consumer that ignores it sees no change; `.passthrough()` means an older cezar sharing the same `~/.cezar/config.json` round-trips it untouched.
- `PATCH /api/v1/projects/:projectId` only widens: every previously-valid body stays valid and means the same thing.
- `runIndexEntry` gains keys; the palette (its only prior consumer) ignores what it does not read.
- `archiveProjectRun` is a new client function over the EXISTING `POST /p/:projectId/runs/:id/archive` route — no server route is added or changed.
- `/tasks` was not a route (the flat `/tasks/:id` legacy redirect is unaffected — React Router ranks the static segment above the `*` that owns it).
- `cezar projects tag` is a new subcommand; no existing spelling changes.
