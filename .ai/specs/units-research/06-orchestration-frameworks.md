context, handles budgets, verifies results, and what their own docs/post-mortems say about
hierarchy vs flat. ~17 searches/fetches; see Sources.

## 3. Findings — what demonstrably works, what demonstrably fails

**Works, with evidence:**

- **Fan-out/fan-in with isolated context + condensed reporting** (Anthropic's research system, Magentic-One's ledger). The mechanism that actually earns the token premium is subagents doing wide, independent exploration and reporting *summaries*, not full transcripts, back up. Anthropic ties 80% of their eval variance to token usage/parallelism, not to the manager being smart.
- **Structured artifacts over chat transcripts** (MetaGPT's publish-subscribe of specs/PRDs/diffs; LangGraph's typed graph state; Magentic-One's dual ledger). Every credible design has moved away from "agents converse" toward "agents read/write typed documents." Free-form group chat (early AutoGen) is the pattern people keep bolting structure onto after the fact (AG2's `ContextVariables` addition, exactly to escape pure-chat state).
- **Deterministic routing where the task allows it** (Google ADK's Sequential/Parallel/Loop agents alongside LLM routing). Not letting an LLM manager decide something a state machine could decide is treated as a maturity signal, not a limitation.
- **Verification as a structural role, not an afterthought** (MetaGPT's QA role; Anthropic's separate citation pass). Where it's baked into the pipeline, it holds up; where it's a bolt-on "critic agent," it degrades to rubber-stamping (see below).

**Fails, with evidence:**

- **LLM-decided hierarchical delegation without deterministic routing is the single most-repeated failure.** CrewAI's hierarchical process is documented (independent benchmark article, corroborated by a GitHub discussion asking "how do I use this correctly") to execute tasks the manager should have skipped, overwrite good outputs with the *last* agent's confused ones, and burn ~2x the tokens/latency of a routed alternative for no quality gain — the fix that worked was replacing LLM discretion with explicit conditional routing logic, i.e., making the "manager" less autonomous, not more.
- **Coordination tax scales with sequential dependency, and manager layers actively hurt on tightly-coupled tasks.** Cited benchmark evidence: multi-agent coordination gave +81% on a parallelizable benchmark but −39% to −70% on a benchmark requiring strict sequential reasoning (PlanCraft) — because inter-agent communication fragments reasoning that needs to stay in one head. This is a direct warning for cezar: a commander splitting a tightly-coupled implementation task across workers is the CrewAI failure mode, not the Anthropic-research-system success mode.
- **Budget/cost control is a genuine, catalogued gap across nearly every framework, not a solved problem anyone can point to.** The 63-incident catalog attributes overruns mostly to retry loops (27), lack of cost observability (22), and delegation fan-out double-spend (11) — and delegation fan-out is exactly cezar's shape (commander → workers → possibly sub-workers). None of the frameworks reviewed here (CrewAI, AutoGen, LangGraph, MetaGPT, OpenAI SDK, ADK) ship a first-class aggregate budget primitive; LangChain/LangGraph's popularity is why it dominates the incident list (33/63), not because it's worse-designed than peers.
- **Verifiers rubber-stamp under time/token pressure ("early victory problem").** Anthropic names this directly: a checker agent told to verify will often mark something as passing after minimal effort unless explicitly instructed to be adversarial/thorough. A `verdict` field alone (cezar's REVIEW kind) doesn't prevent this — the prompt has to fight for it.
- **Full-context handoffs (OpenAI Agents SDK) are cheap to build and expensive to run**, and the SDK's own guardrail design has a documented gap: guardrails don't wrap the handoff call itself, so a bad handoff can skip validation. Any handoff-of-full-context design (cezar's parking/resume across ranks) should ask explicitly what validates the *handoff*, not just the participants.
- **Flat "no real-time orchestrator" teams are the newest and least proven pattern.** Claude Code's own Agent Teams — the closest public analog to cezar's mission directory — is a Feb 2026 research preview with no published claim/lock protocol and secondary coverage that flags the coordination story as underdocumented. This is evidence of direction (the field is moving toward filesystem/flat coordination) but not evidence that the specific mechanics are solved.

## 4. Filesystem / shared-scratchpad communication, specifically

This is where the field is heading, but the evidence is thin on mechanics:

- **Who's doing it:** Claude Code Agent Teams (task-list file, claim-mark-write cycle); the generic "blackboard pattern" described in filesystem-coordination surveys (agents watch a shared workspace, contribute when relevant, no direct agent-to-agent addressing needed); ad hoc community requests for exactly this (e.g., a "Shared State Layer for Persistent Multi-Agent Teams — Domain-Owned File Bus" feature request on a smaller framework, indicating the itch is common enough that people are asking library maintainers for it rather than finding it built-in).
- **Why people reach for it:** stated benefits are persistence across restarts, no direct network coupling between agents, and — specifically for large artifacts — avoiding repeated transfer of big payloads by passing a file path/metadata instead of inlining content into every message. All three map directly onto cezar's rationale (survives restarts, readable by any tool, no schema needed) per its own v2 spec's A1 answer.
- **What's NOT demonstrated anywhere in this research:** a documented, load-bearing conflict-resolution or claim-locking protocol for concurrent writers. Every source either (a) describes the pattern at a conceptual level (Fastio's survey: "one agent writes... another monitors... " — no locking discussion) or (b) explicitly declines to specify it (the MindStudio piece on Claude Code Agent Teams says outright there's no detail on "file locking mechanisms, conflict resolution protocols, work-claiming procedures, race condition handling, stale state management"). The one framework doing this in a shipping product is *also* the one being least transparent about how it avoids double-claims — which should be read as "even the vendor closest to this pattern hasn't published a hardened answer," not as "it's a solved problem cezar can assume works."
- **Cost signal:** the same Claude Code coverage that praises filesystem coordination for parallel pipelines also concedes flat/team coordination is "the most expensive" mode because every inter-agent signal round-trips through a model call — filesystem-as-channel doesn't itself reduce token cost; it just changes what carries the payload. Cheapness has to come from *how much* gets written/read/re-read, not from the fact that it's a file.

## 5. Where cezar's design copies well, where it repeats known mistakes

**Copies well:**

- **Files as the channel, engine as the signal** (mission directory: brief/plan/order/notes/report/inbox, delivery fired on turn-end/session-open edges cezar already owns) is directionally aligned with the strongest pattern in the survey: structured artifacts over chat, and no dependence on a poll/watcher loop. This avoids the vaguest part of every filesystem-coordination write-up found (nobody documents a locking/claim protocol) by sidestepping concurrent-writer conflicts almost entirely — each unit owns its own `order.md`/`notes.md`/`report.md`, and the inbox is append-only per recipient, not a shared mutable list multiple units race to claim. That's a structurally safer choice than "shared task-list file every teammate claims from" (Claude Code Agent Teams' pattern), which is exactly the part nobody — including Anthropic — has published a hardened design for.
- **Isolated-context fan-out with condensed reporting** (a spawned unit gets its own order/notes/report, reports a bounded `suggestions[]` back rather than a raw transcript) matches Anthropic's own research-system pattern, the one best-evidenced success case in this whole survey.
- **Review as a structural role** (a REVIEW-kind unit judging a different unit's branch, commander merges only on `approve`) matches MetaGPT's "verification baked into the pipeline" pattern rather than CrewAI's "manager informally decides it's done."
- **Per-mission resource caps (`parallel`, `maxChildren`) set at mission start** is a real budget primitive at the concurrency layer — something the survey found *no* other framework ships natively (LangGraph, AutoGen, CrewAI all push this to the host app). This is a genuine differentiator, not table stakes.
- **Deterministic engine behavior around markers** (v2's fix: "anchor on the LAST marker occurrence," "a refused marker is delivered back... as a re-prompt") is the same instinct as Google ADK's workflow-agent/LLM-routing split — narrowing where an LLM gets discretion, after finding out the hard way (v1's marker-parser refusals) what happens when it has too much.

**Repeats known mistakes / open risk:**

- **Escalation "one rank at a time" through inboxes is a full-context-style handoff chain**, structurally similar to OpenAI Agents SDK handoffs — and that survey's sharpest documented gap is that handoffs bypass guardrail validation. Cezar's `CEZ:ASK`→commander→(possibly further up)→Guard chain should be checked for the same class of gap: does anything validate a question/answer crossing a rank boundary, or only the endpoints (the unit asking, the human answering)? The v2 spec's "not shipped" list already flags lineage-tracked retries and settle-time branch checks as open — these are exactly the shape of gap the survey found costs people.
- **The `verdict` field on REVIEW units is vulnerable to the "early victory problem"** the Anthropic post names explicitly: a reviewer prompted to approve/reject will tend toward approving unless the prompt actively fights that tendency (adversarial instructions, explicit failure-mode checklist). Nothing in the v2 spec (per `.ai/specs/2026-09-09-units-v2.md`) suggests the REVIEW kind's prompt currently does this — worth an explicit check against `packages/cezar/src/units/prompts.ts`.
- **Budget release/charging trusts self-reported completion.** v2 charges a settled child "its actual cost" and returns unspent budget to the parent — but the 63-incident catalog's largest single cause after retry loops is *lack of cost observability*, and the second-largest delegation-specific cause is *fan-out double-spend under concurrency*. A commander spawning several children under a mission `parallel` cap, where a child's actual cost is only known/charged at settle time, has the same window the catalog describes: cost is invisible mid-flight, and a runaway child (stuck in its own retry loop) isn't stopped by the mission's concurrency cap, only by its own per-run budget. Worth confirming cezar has a *live* per-unit spend check, not just a settle-time charge — concurrency limits (`parallel`, `maxChildren`) cap how many units run, not how much any one of them can burn before it's caught.
- **Sequential/tightly-coupled work routed through a commander→worker split risks the CrewAI/PlanCraft failure mode**, not the Anthropic-research success mode — the benchmark evidence is specifically that manager-mediated delegation *helps* on parallel, independent subtasks and *hurts* (−39% to −70%) on tasks needing continuous sequential reasoning. cezar's units feature should have (and the caller should verify it has) guidance — in the commander's prompt or in product framing — steering commanders away from splitting a single tightly-coupled implementation into worker pieces just because delegation is available. Nothing found in the v2 spec addresses this task-shape judgment explicitly.
- **The mission root escalating to `review` and a draft-PR nudge are both listed as "not shipped"** in v2 — i.e., the verification loop that closes a mission (reviewer catches a problem → mission root sees it → mission root can act) isn't complete yet. Given how load-bearing verification-as-a-structural-role is in every framework that gets it right (MetaGPT, Anthropic), this gap is worth prioritizing over new delegation surface area.

## 6. Implications

1. Treat the mission directory's per-unit-owned files as the load-bearing safety property it is — resist any future change that turns `order.md`/`report.md`/inbox files into a shared mutable list multiple units write to concurrently; that's the one thing no filesystem-coordination framework in this survey has a published, working answer for.
2. Add or surface a live per-unit spend check independent of `parallel`/`maxChildren`, and make mid-flight spend observable (not just charged at settle) — this is the single most-evidenced, most common failure class in the entire survey (49/63 incidents are retry-loop or cost-observability).
3. Give REVIEW units an explicit anti-rubber-stamp instruction (a checklist they must falsify against, not just "approve or reject") — cheap to add, directly targets a named, documented failure mode.
4. Put task-shape guidance in front of delegation: a commander prompt (or cockpit UI hint) that flags "this looks sequential/tightly-coupled — are you sure delegation helps here?" would encode the PlanCraft-benchmark lesson before a user learns it the CrewAI way.
5. Prioritize closing the review→mission-root escalation loop (already flagged as not-shipped) before expanding delegation breadth (more ranks, more kinds) — verification-as-structure is the differentiator that correlates with frameworks that hold up; delegation breadth without it is the CrewAI trajectory.
6. When documenting cezar's filesystem-channel design publicly, be explicit about what makes it safe (per-unit file ownership, append-only inboxes) rather than claiming the pattern is proven in general — the survey found the opposite: filesystem coordination is directionally hot but mechanically undocumented industry-wide, including by the vendor (Anthropic/Claude Code) closest to it.

## 7. Confidence and gaps

- **High confidence:** the token-cost multipliers for multi-agent systems (Anthropic's own 4x/15x figures), the CrewAI hierarchical-mode failure description (corroborated by an independent benchmark article and a GitHub discussion asking the same "how do I use this" question), and the existence of a real, catalogued budget-overrun failure class across frameworks (63-incident paper) — these came from either primary vendor docs or a specific empirical study, not just blog consensus.
- **Medium confidence:** the PlanCraft/Finance-Agent benchmark numbers (+81%/−39–70%) — read from search summaries of a benchmarks-survey blog post, not the primary papers; treat the direction (sequential tasks punish manager layers) as solid, the exact percentages as illustrative.
- **Low confidence / explicit gap:** Claude Code Agent Teams' actual coordination mechanics (locking, claim protocol, conflict handling) — every source either declined to specify or admitted it isn't documented. This is the single most relevant comparator for cezar's mission directory and it's also the least verifiable thing in this report; if it matters for a design decision, it needs primary-source confirmation (the feature's own docs/changelog, not secondary coverage), not this file.
- **Not covered / would need more budget:** OpenAI Agents SDK production post-mortems (only got docs, not community failure reports); Google ADK community/GitHub-issue evidence (only got vendor blog content, no adversarial community source); MetaGPT community abandonment signal (the paper and docs were covered, but no GitHub-issues-style evidence of teams dropping it was found in the searches run). A follow-up pass with a larger budget should target GitHub issue trackers directly (not blog summaries of them) for CrewAI, LangGraph, and AutoGen to get first-party failure reports rather than secondary syntheses.
