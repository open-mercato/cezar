Reconnect an agent account right where the error appears

Today an expired login leaves one red line in the chat. This design replaces it with a card that signs the account back in on the spot: in a new browser tab, with a device code or a pasted key, depending on what the agent supports. When the sign-in finishes, the turn that failed carries on, and so does everything else that was waiting on that account.

Desktop

Everything in the mockups responds to clicks: the card's buttons move it through its states, and the dashed demo buttons inside a sign-in simulate the vendor's answer.

Mobile (CezarBot and the cockpit on a phone)

A phone is always remote, so a sign-in that only calls back to localhost can't work there. The phone gets the device code, a paste-the-code step, or a link that works on any device. An agent that can only sign in on the computer itself gets a Finish on your computer hand-off instead.

What the card offers

Actions, in order of weight

  1. Reconnect <account> is primary. It starts the agent's own sign-in for that account (same config folder as the failed run, so the session can resume).
  2. Use <other account> instead is a split button listing the healthy accounts this task or manager is allowed to use, in the account picker's order. Signed-out accounts are shown greyed with their state. One click switches and retries. A task switch starts a fresh session, as Continue with another account already does (agent-profiles spec § sessionId/profileId). The menu says so.
  3. More options holds Already signed in? Check again, Open Settings → Agent accounts, and last, Sign in in a terminal with the exact command and Copy.

One card per account, never per failure

Five tasks on one dead account show one live card: the newest occurrence. Older occurrences collapse to a quiet line, "Claude Code · Work was signed out here (reconnected 10:51)". Then a chat with a long history doesn't fill up with red, and one click unblocks everything.

Resume: everything, automatically (decided 2026-11-18)

When the account is signed in again, every task and manager blocked on it restarts by itself: the turn whose card you clicked, the other parked tasks, and the managers whose chat turn failed on it. There is no "Resume" or "Resume all" step and no setting.

Each restart is a model call nobody clicked for, so the spec records it as an unattended cost (AGENTS.md § Zero config). The restarts are bounded: only items parked with reason auth on that account, each resumed once per reconnect, with tasks still going through maxParallel. A stopped or archived task is not blocked any more and doesn't restart. Watch and job turns are not re-run; their next tick runs normally.

How the user learns about the rest

  • The success state lists them while they restart: "Also resuming on Work: 2 tasks, 1 manager", each with a link.
  • A toast confirms it ("Resumed this turn and 3 more"), with a link to the attention list.
  • Every other blocked chat or transcript shows the quiet line "✓ Reconnected Claude Code · Work · resumed", so a user who opens it later sees why it moved.
  • The attention list's "Sign-in needed" group empties, the sidebar badge clears, and the banner goes away. All of it is driven by the same provider-status SSE event.

Mechanism, per agent

One new server object, a login session, wraps whatever each vendor offers. It reuses resolveWorkspaceProfile, providerAuth.loginCommand, the account folder, and watchOpenedLogin from POST /providers/connect. What it adds is the vendor's prompt (URL, code, key request) relayed to the card, in place of a terminal window. The rows marked “spike” must be confirmed against the installed CLI before Phase 2 relies on them. Where a spike fails, that agent keeps today's terminal hand-off, which the card still drives and watches.

Lifecycle of a login session

click Reconnect→POST /providers/login→spawn vendor login in the account folder→SSE agent-login: url / code / needs-input→user approves→CLI exits 0→fresh status probe (same account)→identity check→clear incident · SSE provider-status→resume
  • Detecting success relies on the vendor CLI, never on cezar reading tokens. Signs of success: the login process exits 0 (or Codex's account/login/completed, or OpenCode's auth callback), then a refreshed profileStatus must answer connected. For terminal-only agents, the existing watchOpenedLogin probes (15 s … 15 min) are the signal.
  • Account mismatch: readAccountIdentity compares the new login with the one the account had. A different email is reported as a failure, "Signed in as another account than Work used". It does not count as success, because otherwise a task would quietly continue on someone else's plan.
  • Clearing the latch: a completed login started by the user is the "evidence of a fresh login" the provider-auth spec asks for, so it clears that account's runtime incident (clearRuntimeAuthFailure / recheckProfileAuthFailure). No other path does.
  • Timeouts: a session ends at the vendor's code expiry, or after 15 min, on Cancel, or when the card unmounts with no other viewer. The process tree is killed. Only one session runs per account; a second click joins it.

Resuming what was blocked

  • Tasks: an auth rejection already writes provider-auth-required. Phase 2 also parks the run in waiting with reason auth (attention list, "needs you") instead of only failing, and keeps sessionId + steps[].profileId. Resume is the existing POST /runs/:id/continue on the same account, so it reuses the same session and the agent continues with "continue where you stopped". A failed run from before this change gets the same card, and its Resume is Continue.
  • Managers: resuming re-sends the failed chat turn (today's Try again, onRetry). Failed watch or job turns are not re-run; the next tick runs.
  • Who is blocked is found by a server index: runs parked with reason: auth plus managers whose last turn failed auth, both keyed by (provider, profileId). It is returned with the login session's success event, which is how the card can say "Also waiting: 2 tasks, 1 manager".
  • Switch account: for a manager, PATCH its agentProfile (the same field as the gear's Account picker), then retry. For a task, Continue with agentProfile starts a fresh session (spec 2026-07-29). The choices are limited to the manager's or project's allowed accounts and to connected rows.

Security

  • No token ever reaches page JavaScript. The vendor CLI completes the OAuth exchange and writes its own credential store in the account folder. The page only sees: phase, a verification URL, a short user code, an expiry time, and a fixed error reason.
  • URLs are allow-listed per agent (for example claude.ai, auth.openai.com, cursor.com, github.com/login/device). A shimmed or compromised CLI can't send the user to a phishing page through cezar. Links open with noopener.
  • Pasted codes and API keys travel once in a POST body and go straight to the CLI's stdin (or OpenCode's own auth API). They are never persisted, logged, echoed, put into SSE/NDJSON, or sent to telemetry. The field uses type=password, autocomplete=off.
  • Inputs are closed: the provider enum and account id select a server descriptor. No request text becomes an argument (same rule as Connect).
  • Remote cockpits: starting a login on the host from elsewhere is new exposure. A paired phone (an authenticated relay channel) and a local cockpit can do it. A hosted web cockpit can do it for named accounts only under the existing CEZ_REMOTE_AGENT_ACCOUNTS=1 opt-in. Otherwise it gets today's copy-the-command 409. The cross-origin guard and the accountsEnabled() refusal keep their current order.
  • Dry-run: CEZ_DRY_RUN=1 uses a mock login session (a fake code, then success after 3 s) and starts no CLI.

API sketch (zod in packages/contract, chained into the providers family)

POST   /api/v1/providers/login
       { provider, profileId?, method?: 'auto'|'device'|'paste'|'key'|'terminal' }
    →  { sessionId, method, url?, userCode?, expiresAt? }   | 409 { error, command }
POST   /api/v1/providers/login/:sessionId/input   { code } | { apiKey, keyProvider? }
DELETE /api/v1/providers/login/:sessionId
SSE    workspace 'agent-login'
       { sessionId, provider, profileId, phase:
         'waiting-browser'|'waiting-code'|'needs-input'|'verifying'|'connected'|'failed',
         url?, userCode?, expiresAt?, reason?, unblocked?: { runs, managers } }
POST   /api/v1/providers/:provider/resume-blocked  { profileId, runIds?, managerIds? }

POST /providers/connect stays as it is: Settings keeps working, and it remains the terminal fallback. Settings → Agent accounts' Sign in again then uses the same login session, so both surfaces share one flow.

Decisions (2026-11-18)

  1. Resume: everything blocked on the reconnected account restarts automatically; there is no Resume step.
  2. Parking: an auth rejection parks the task as waiting (reason auth), resumable and showing the reconnect card. It no longer ends failed.
  3. Hosted web: starting a host sign-in needs CEZ_REMOTE_AGENT_ACCOUNTS=1. Paired phones and the local cockpit can always do it.
  4. API keys: the paste field is offered only for Codex and OpenCode, which store the key themselves. Cursor and Gemini keep env-only keys, and cezar never stores one.
