# Task tags: a personal tag registry for tasks — tag at creation, edit any time, filter by tag

- Date: 2026-11-23
- Category: feature
- Priority signal: medium — the owner regularly starts batches of related tasks (e.g. eight code reviews, several tasks on one feature) and has no way to group or find them beyond Active/Archived.
- Risk signal: medium — new per-user state file plus a new optional field on run records and new API surface; reverses a recorded design decision (2026-08-10).
- Routing: Next: om-auto-write-spec "Task tags: a personal tag registry for tasks, tag at creation and any time after, filter by tag — brief: .ai/specs/briefs/2026-11-23-task-tags.md"

## Problem

A user often starts several related cezar tasks at once — eight code-review tasks, or a handful of tasks on one feature — sometimes by hand, sometimes by asking a running task to start them through the API. The task list offers only Active and Archived, so there is no way to mark those tasks as belonging together and view them as a group. Other users may want to mark tasks for their own reasons (including a do-it-yourself status flow), so the mechanism must be a general tagging system, not a one-off batch field.

## Agreed direction

Add **task tags**: a per-user tag registry, tags applied to tasks by id, editable at creation and at any time after, and a tag filter in the task lists.

- **A tag is an entity**: `id`, `name`, optional `color`, optional `description`, and a **scope** — global (no project) or one project (`projectId`). Typing a new name in the picker creates the tag inline; no Settings trip is required first. Tags can be renamed / recolored / described / deleted later.
- **Storage**: all personal, one file in `~/.cezar` (its own file, like `agent-accounts.json`, never a key in `config.json`), through `cezarHomeDir()`.
- **A task stores tag ids plus a name snapshot** (optional field on the run record). The registry wins when the id resolves; the snapshot is the fallback when `~/.cezar` was wiped (zero-config: deleting state degrades, never breaks). Rename needs no rewrite of run records.
- **Several tags per task**, but the UI is optimized for the one-tag case.
- **Composer placement**: a dashed `+ Tag` chip in the composer's main row next to `+ Skill`, same picker style, selected tags shown as colored chips. **Not** in the Options panel — that panel is "remembered for <project>" and a sticky tag would silently tag later unrelated tasks. The picker lists this project's tags first, then global ones, recently used first.
- **Edit any time, any state** (queued, running, waiting, done, archived): tag chips + `+` in the task header, a "Tags…" item in the task-list row context menu, and an API/CLI to set a task's tags.
- **API**: `tags` on the task-creation input (`createRunInputSchema`) and a route to change an existing task's tags; a `cez` CLI command an agent can call.
- **Filtering**: a task-tag filter in the project task list (beside Active/Archived) and a separate **"Task tags"** filter row on the global `/tasks` page. Multiple selected tags OR together (as existing facets in `packages/web/src/lib/task-filters.ts` do).
- **Tags are a lens only** — cezar never routes, queues, limits or acts on them (same principle as the 2026-08-10 project tags).
- **Reversal stated explicitly**: `.ai/specs/2026-08-10-global-tasks-and-project-tags.md` rejected "tag runs instead of projects" (applied by hand forever; no home because run records live per repo). The by-hand cost is the point here (tasks are tagged deliberately, batch tagging via the API), and the "no home" objection is answered by the registry living in `~/.cezar`. The new spec must cite and answer that rejection.

Rejected:
- **Build nothing / group by dispatching parent** (`dispatch.rootRunId`): only covers dispatched children; most related tasks are started by hand or as independent tasks. The owner needs tags regardless.
- **One group per task**: too narrow; others will want to mark tasks with several tags.
- **Bare-name tags with usage-derived scope**: rejected because tags need rename without rewriting tasks, plus color and description.
- **Merging with project tags / inheritance**: the owner explicitly does not want a project's tags applied to every task of that project (a redundant tag on every task) — not as chips and not in filter matching.
- **Committing project-scoped tag definitions into the repo**: storage is personal only.

## Resolved unknowns

| Question | Answer (from the conversation) |
|----------|--------------------------------|
| One group or several tags per task? | Several tags per task (a full tagging system); UI optimized for the one-tag case. |
| Bare names or entities? | Entities with stable `id`; name, optional color, optional description. Tasks reference ids. |
| How are tags created? | Inline by typing a new name in the picker (composer or edit picker); management (rename/recolor/describe/delete) also available. |
| Global or per-project? | Both: a tag is global (no `projectId`) or scoped to one project. Picker shows project tags first, then global. A name is unique (case-insensitive) among the tags visible in one project; typing an existing name reuses that tag. |
| Where are tag definitions stored? | All personal, one file in `~/.cezar` via `cezarHomeDir()`; nothing committed to the repo. |
| What does a task store? | Tag id + name snapshot. Registry wins when present; snapshot is the fallback when the registry is missing/wiped. |
| Relation to existing project tags? | Separate concept, "same shape, two lists". Project tags stay EXACTLY as today in this spec (plain names, Settings editor, `GET/PATCH /api/v1/projects` `tags: string[]`, `cezar projects tag`). Never inherited by tasks. Migrating project tags to the same entity shape is a possible later follow-up; build the task-tag code so it could be reused. |
| `/tasks` page filters | Two separate rows: "Project tags" (unchanged behavior) and "Task tags" (matches only a task's own tags). |
| Where in the composer? | Main row, `+ Tag` chip after `+ Skill`; not in the sticky Options panel; not remembered across tasks. |
| Can a running task be tagged? | Yes — any state, via task header, list-row context menu, and API/CLI. |
| Multiple selected tags in a filter | OR (any), consistent with existing facets. |
| Deleting a tag | Registry keeps a tombstone for the deleted id so tasks hide it (the name snapshot must not resurrect it); no rewrite of every repo's `runs.json`. |
| Concurrent edits on a running task | Edits are add/remove deltas, never whole-list replacement from a possibly stale cache (the 2026-08-10 "lost tag" lesson). |
| Kanban / status flow | Separate feature, out of scope. Users may use tags however they like; cezar never acts on them. |
| Delivery | All at once — one spec, one implementation (registry, color/description, management, composer, editing, filters, API/CLI). |

## Non-goals

- Applying or inheriting project tags on tasks, in display or filtering.
- Changing project tags' storage, shape, API, CLI or Settings editor.
- Letting a task start **independent top-level** tasks (today `cez task create` only creates dispatched children). That is a separate feature; only `tags` on the existing creation input/routes is in scope here.
- Kanban / workflow-status columns, or any engine behavior driven by tags (routing, queues, concurrency).
- Sharing tag definitions with a team (repo-committed tag files).
- Grouping the task list by tag (fan-out sections); filtering is the requirement.
