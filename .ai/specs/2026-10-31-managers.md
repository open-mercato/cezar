# Managers

A manager is a global, long-lived agent you chat with instead of visiting each repository. It
watches the repositories connected to it, tells you what needs you, starts and steers tasks, sets
up workflows and automations, and proposes merges. Tasks stay where they are; a manager is the
touching point above them.

Design: `assets/manager/` (`code-mode`, `first-manager`, `manager-chat`, `settings-dropdown`,
`composer-reference`). Figma: file `PyqjDBSreTwXbJZdFtqngY`, node `37-2`.

## Surface

- **Code | Manager switch** in the sidebar under the brand. It is a mode derived from the URL
  (`/manager*` = Manager), not stored state. Manager carries a dot when any manager is unread or has
  a pending approval. Code mode is the existing sidebar, unchanged.
- **Manager mode sidebar**: manager rows (avatar, name, time, one-line preview, unread dot) and a
  new-manager button. The footer row (Tools, version, star, settings, theme) stays; CPU/RAM and
  search are Code-mode only, as in the design.
- **`/manager`** opens the most recent manager, or the first-manager setup when none exists.
- **`/manager/new`**: "Setup Your first manager" with a prompt box and three pickers (projects,
  model + effort, account). Submitting creates the manager and sends the prompt as its first
  message. Presets fill the box for the common jobs ("Watch my repositories…").
- **`/manager/:id`**: title, projects line, gear (dropdown: projects, model + effort, account,
  chron, plus rename, jobs, delete). The chat: user bubbles, assistant markdown, a collapsed "Ran N
  commands" row, session cards (`[[task:…]]`: title, +/− stats, status, chevron into that task's
  thread) and approval cards. A scroll-to-bottom button, a composer with `/` commands, and a footer
  under it: `Chron: 15 min`, `Opus 5.5 Medium`, a working spinner.
- Opening a task from a card leaves a **Back to <manager>** link on the task (router state), so the
  manager stays the way home.
- Mobile: list and chat are separate screens, composer per `composer-reference`.

## Model

`~/.cezar/managers.json` holds definitions (`managerSchema`); `~/.cezar/managers/<id>/` holds
`chat.ndjson` (append-only, replace by message id), `state.json` (session id, cursors, reported
attention keys, cost) and `workdir/` (the agent's cwd). Same rules as every workspace file: every
path through `cezarHomeDir()`, zod with `.catch` per entry, atomic merge-writes, a corrupt file
degrades to empty with one warning, and deleting the directory loses history, never boot.

## Turns

A turn is one `createRunner(runner).startSession(spec, …, { autoEndAfterFirstTurn: true })`, resumed
with the manager's session id, so a chat survives restarts and costs nothing while idle. One turn
per manager at a time; messages sent meanwhile queue and run next, folded together. `Stop`
interrupts. A resume failure starts a fresh session with a recap of the last messages rather than
wedging the chat. Crash recovery: a message left `streaming` at boot is closed as stopped.

`CEZ_DRY_RUN=1` must produce a scripted turn through the runner's mock: a command, text with a
`[[task:…]]` card, an action proposal when asked to merge. E2E and screenshots depend on it.

## Watching

Every `cronMinutes` a manager takes a **snapshot** of its connected projects (tasks from the
existing stores; PRs via the same forge calls the GitHub tab uses, cached and degradable) and
derives attention items with stable keys. **No new key, no model call** — a quiet repository costs
nothing; this is the brake that makes a 15-minute default affordable. With new keys it runs a
`watch` turn; the agent replies `MANAGER:QUIET` when nothing deserves the user, and that turn leaves
no message. The cadence timer arms only for an existing manager with `cronMinutes > 0`, never
catches up on missed ticks, and a tick skips a manager whose turn is running. `Check now` forces one
and ignores the key gate. Two cockpits on one home must not both fire: take a per-manager lease.

Jobs (`managerJobSchema`) are saved prompts on their own interval, run as `job` turns through the
same queue.

## Safety

- **Scope**: every tool route refuses a project the manager is not connected to.
- **Approval**: merging, enabling an automation and adding a job are proposed (`action` message)
  and only the cockpit's `decision` route performs them, through the same code the GitHub tab
  uses. The guard is load-bearing: a watch turn reads PR text written by anyone, so a merge must
  never be one prompt injection away. Cards are pinned: the server stamps title and head sha or
  definition and revision, and a change after the proposal refuses. No autonomy knob in v1.
- **Tasks are the known limit**: a task a manager starts is an ordinary task with a full shell, so
  it could run `gh pr merge` itself. Its system prompt forbids that and nothing enforces it. Chat
  turns have the user present; jobs are prompts the user wrote or approved. Decided: tasks stay
  startable from both, because "start a task" is the manager's main verb.
- **Transcripts are separate**: watch and job turns keep their own sessions, so text they read is
  not live in a later turn that can act.
- **Watch turns are read-only**: the server refuses `task`, `task-message` and proposals during a
  `watch` turn. It may ask the user to act; it may not act. Prompts/PR text in the snapshot are
  fenced as untrusted data.
- **Tools**: `allowedTools` Read/Grep/Glob/Bash with a `bashAllowlist` of the `cez-manager` shim
  and read-only `gh` (no `git`: the cwd is no repository, and `git log --output` writes files). Enforced on Claude; other backends do not honor `allowedTools` (#430),
  so there the prompt is the only fence. Say so in the UI docs rather than imply otherwise.
- **Feature flag**: `CEZ_MANAGERS=0` removes the mode, routes (409) and timers. Default-on is safe
  because nothing runs until the user creates a manager; a pending owner ratification is recorded
  in AGENTS.md.

## `cez manager` (the agent's tools)

Addressed like `cez task`: `CEZ_API_URL`, plus `CEZ_MANAGER_ID`. `status`, `attention`, `tasks`,
`task <run>`, `task create`, `task say`, `prs`, `merge` (proposes), `automation …` (delegates to
`cez automation` with the project pinned; it never enables, an edit pauses, enabling proposes), `workflows`,
`job list|remove`, `job add` (proposes). `cez-manager` is a shim on the turn's PATH so the allowlist can name it.

## Not in v1

Attachments in the manager composer (the `+` opens nothing until a runner path needs it), manager to
manager delegation, per-manager budgets, Slack/email delivery, autonomous merges.

## Tests that matter

Store corruption and salvage; key gate (no new key → runner never called); restart recovery;
queueing; scope and watch refusals; merge only through `decision`; contract parity; every route in
BACKWARD_COMPATIBILITY.md §2; sidebar mode from URL; first-run flow; a chat with cards from a
fixture; an e2e walk in dry-run with screenshots.
