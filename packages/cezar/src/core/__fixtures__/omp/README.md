# omp RPC fixtures

Every `*.ndjson` here is a **real** `omp --mode rpc` transcript, captured on
2026-09-28 against **omp 18.4.2** (Homebrew, `can1357/tap`) — the same wire a
cezar run spawns. Captured by driving the CLI through a scripted stdin
prompt in a throwaway directory; nothing was hand-authored. The only edit:
a provenance header line (`{"fixture": …}`) added as the first frame, which
the mapper skips like any unknown frame.

Protocol reference: `docs/rpc.md` shipped with the omp CLI (also published at
https://omp.sh/docs/rpc). The wire is the continuation of pi's RPC protocol,
so these fixtures sit beside pi's (`__fixtures__/pi/`), adding the frames pi
does not have (`toolcall_*` inside `assistantMessageEvent`, `prompt_result`).

Every transcript was run with `--no-ui` so the run never owed extension
dialogs; the host key and prompts are the captured ones (keys are not part of
the stdout protocol and appear nowhere).

| Fixture | Scenario | Covers |
|---|---|---|
| `tool-lifecycle` | `get_state`, then read → edit (old_string→new_string) → failing bash (exit 3) → reply | `session.started`; thinking → `reasoning` items; `toolcall_*` → tool item `pending`, `tool_execution_*` → `running`/`completed`/`failed`; `tool_stream_update` → `item.updated` with `diffs`; `message_end` usage; `prompt_result` → `turn.completed` |
| `plan-todos` | todo tool `init` + `done` ops across the run, read, bash (exit 0), reply | `toolcall_end` for `todo` → `plan.updated` (all pending); each `tool_execution_end` carries `details.phases` → full-replacement `plan.updated` with real statuses |
| `abort` | long essay prompt, `abort` mid-turn | `prompt_result` with `status: "aborted"` → `turn.completed` `stopReason: cancelled` |
| `session-error` | `set_model` to a nonexistent id, then a normal prompt | command-level `response success:false` (string error) → `session.error` non-fatal; run still completes |
| `subagent` | one `task`-tool subagent spawn then `wait` for it | task item `pending`→`running`→`completed` (`toolKind: 'task'` via the shared tool display — the parity nesting row); live child progress streams through `tool_execution_update` |

`*.expected.json` are the **exact** `UiEvent[]` the mapper produces for each
transcript — generated by replaying the fixtures through
`omp-ui-mapper.ts` (`omp-ui-mapper.test.ts`), never hand-written. The same
`.expected.json` files feed the parity test (`ui-parity.test.ts`).
