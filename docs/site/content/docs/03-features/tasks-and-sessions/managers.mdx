A manager is a global, long-lived agent you chat with instead of visiting each repository. It watches the projects connected to it, tells you what needs you, starts and steers tasks, sets up automations, and proposes merges. Tasks stay where they are, and the manager is your point of contact above them. No project owns a manager, and you can create several.

## Where to find it

Sidebar → Tasks | Manager switch → Manager

The switch sits under the brand in the sidebar, and the mode comes from the URL:

| Mode | What the sidebar shows |
| --- | --- |
| Tasks | Your projects and tasks. |
| Manager | One row per manager with its latest message, and **New manager**. |

A dot on **Manager** means a manager has an unread message or an approval waiting. The command palette also lists **Manager**, **New manager**, and each manager by name.

## How to use it

1. Open **Manager**. With no manager yet, Cezar shows **Setup Your first manager**.
2. Describe the job in **What should this manager do?**, or pick a preset: **Watch my repositories**, **Keep PRs moving**, or **Run big tasks**.
3. Choose the projects, model, effort, and account, then select **Create**.

Your text becomes the manager's standing instructions and its first message, so it starts working right away. Each manager gets its own character in the sidebar. To change its character, name or instructions later, open the gear and select **Persona…**.

Type `/` in the chat for commands:

| Command | What it does |
| --- | --- |
| `/status` | Gives a short status of the connected projects. |
| `/attention` | Lists what needs you now. |
| `/tasks` | Lists running and recently finished tasks. |
| `/prs` | Lists open pull requests and what each one waits for. |
| `/check` | Runs a watch check now. |
| `/stop` | Stops the current turn. |

The manager handles one turn at a time. Messages you send during a turn run next, folded into one turn. A manager runs only for a turn, so an idle chat costs nothing and survives a restart.

## Connect repositories

A manager starts with **All projects**, which covers every project registered in Cezar, including projects you add later. To limit it, open the projects picker under the manager's name and select individual projects. The chat records each change, for example *Connected to api, web*.

Cezar refuses any `cez-manager` command that targets a project the manager is not connected to. An approval also fails if you disconnected its project after the manager proposed it.

## Refresh

**Refresh** sets how often a manager checks its connected projects. The default is 15 minutes. Change it in the footer under the composer: **Off**, 5, 15, or 30 minutes, 1 or 4 hours, or 1 day.

A check reads the task stores and the same GitHub data the GitHub tab uses, then looks for attention items:

| Source | Attention item |
| --- | --- |
| Tasks | A task, including a dispatched subtask, waits for your answer. |
| Tasks | A task failed in the last 7 days, or reached review, and you have not opened it since. |
| Tasks | A running task has shown no activity for two hours. |
| Pull requests | A pull request that is not a draft has a conflict or failing checks, is ready to merge, or waits on a review. |
| Automations | An enabled automation's newest log line is an error. |

**A quiet check costs nothing.** With no new attention item, Cezar makes no model call and leaves no message. A new item starts one model turn. The manager then tells you what deserves your attention, or decides that nothing does and stays silent. You pay for that turn in both cases.

Cezar reports each item once. The same task failing again is a new item, and so is a pull request problem that cleared and came back.

**Check now** in the gear menu and `/check` skip that gate, so they always run a model turn. When nothing needs you, the chat shows *Checked: nothing needs you right now.*

> **Good to know**:
>
> - Checks run while Cezar runs. Checks missed while it was closed collapse into one.
> - After a failed check, the interval doubles, up to 16 times the Refresh setting. The chat shows one error line for the whole run of failures.
> - Connected projects with no GitHub access still get task checks.

## Jobs

A job is a saved prompt the manager runs on its own interval, for example a morning summary of open pull requests. Open the gear, select **Jobs…**, then add a name, a prompt, and an interval from 5 to 10,080 minutes. You can also ask the manager in chat to add one, and it proposes the job as a card you approve. A manager holds up to 32 jobs.

Replies from a job carry a *Job:* label with its name in the chat. Jobs ignore the attention gate and keep running with **Refresh** set to **Off**, so **every due job spends a model turn**. Use the switch in **Jobs…** to pause a job.

## What a manager can do

| Action | Chat and job turns | Watch checks |
| --- | --- | --- |
| Read tasks, pull requests, workflows, and automations | Does it | Does it |
| Start a task, with a workflow or Dispatch | Does it | Refused |
| Message a running task, or continue a finished one | Does it | Refused |
| Create or edit an automation, which always leaves it paused | Does it | Refused |
| Add a job | Proposes it | Refused |
| Remove a job | Does it | Refused |
| Merge a pull request | Proposes it | Refused |
| Enable an automation | Proposes it | Refused |

A watch check reads text that anyone can write in a pull request, so Cezar keeps it read-only. It can ask you to act, and you then ask for the action in chat.

Merging, enabling an automation and adding a job happen only when you approve. The manager puts a card in the chat with its reason. Select **Approve** or **Reject**, and the manager learns the outcome on its next turn.

Approving a merge goes through the same merge route as the GitHub tab, with the method the manager proposed or the repository's default. The card is tied to the commit you were shown. If someone pushes after the proposal, the merge fails instead of landing code you never saw. An automation card shows the definition and is tied to it the same way, so an edit after the proposal fails too.

## Send screenshots and files

Paste a screenshot, drop a file on the chat, or select **+** in the composer, including on the setup screen. The manager sees images directly and gets every file as a path it can read, then and in later messages. Deleting a manager deletes its attachments.

## Answer a manager's questions

When a manager needs a decision from you, it shows a question card with clickable choices, its recommended choice first. Every question also offers **Other…** and **Need more info**. A reply typed in the chat answers the card too.

## Choose read-only or write access

Each repository a manager connects to has its own access, which you set in the projects picker. **All projects** sets it for everything the manager reaches, and a project's own setting overrides that. New managers have write access.

On a read-only repository, the manager still sees its tasks and pull requests, and can start tasks that answer questions. Those tasks can run on any agent, can't change files and can't push or open pull requests. The manager can't dispatch, merge, enable or set up automations there, and an approval card already waiting fails once you lower access. Tasks already running keep the access they started with.

## Notifications

Everything a manager writes appears in its chat with an unread dot. When it judges something important, such as a task blocked on you or a big task finishing, it also raises a system notification. So does any approval or question card. On your own Mac, Windows or Linux machine this is the operating system's notification and needs no open tab. On a hosted Cezar it is a browser notification, which you turn on in Settings. If you are reading that chat, Cezar does not notify you.

To silence a manager, open the gear and turn off **Notify me when important**.

## Open a task from a card

Every task the manager names or starts appears as a card in the chat. A card shows the task's title, live status, and added and removed lines. Dispatched tasks appear as their root task, and you can ask the manager about the subtasks.

Select a card to open that task's own thread and keep working there. The task then shows a `Back to <manager>` link, which stays for the browser session as you move between the task's tabs. A pull request chip opens the pull request in the GitHub tab.

## Tool limits by agent

Cezar gives a manager `Read`, `Grep`, `Glob`, and a `Bash` allowlist of `cez-manager` plus read-only `gh` commands. **Only Claude enforces those limits.** Choose Claude for a manager that reads pull requests from people you do not trust.

| Agent | What limits the manager |
| --- | --- |
| Claude | The agent CLI denies every tool and command outside the list. |
| Pi | Pi has no per-command allowlist, so Cezar removes `Bash`. The manager can read files but cannot run `cez-manager`, so it has no tasks, proposals, or status commands. |
| Every other agent | The system prompt is the only limit. These agents ignore the tool list and can run any command the agent allows. |

On every agent, Cezar's own routes still refuse what they should: out-of-scope projects, actions during a watch check, and a `cez-manager` merge without your approval. Those rules guard `cez-manager` only. An agent that ignores its prompt can still call `gh pr merge` directly, because nothing on that agent blocks the command.

> **Good to know**:
>
> - Managers are available by default, and nothing runs until you create one. The default 15-minute Refresh then spends tokens only when a check finds a new item.
> - `CEZ_MANAGERS=0` turns managers off. It removes the Manager mode, stops the timers, and makes the API answer `409`. Cezar reads it at boot, only the exact value `0` opts out, and your managers stay in `~/.cezar/` for when you turn the feature back on.
> - Definitions live in `~/.cezar/managers.json` and chats in `~/.cezar/managers/`. Deleting a manager removes its chat and jobs. Tasks it started stay where they are.
> - The effort picker applies to Claude only.
> - Managers have no autonomous merges and no per-manager budget.
