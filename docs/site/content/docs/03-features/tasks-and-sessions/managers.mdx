A manager is a global, long-lived agent you chat with instead of visiting each repository. It watches the projects connected to it, tells you what needs you, starts and steers tasks, sets up automations, and proposes merges. Tasks stay where they are, and the manager is your point of contact above them. No project owns a manager, and you can create several.

## Where to find it

Sidebar → Tasks | Manager switch → Manager

The switch sits under the brand in the sidebar, and the mode comes from the URL:

| Mode | What the sidebar shows |
| --- | --- |
| Tasks | Your projects and tasks. |
| Manager | One row per manager with its latest message, and **New manager**. |

A dot on **Manager** and on each manager's row means it wants you: amber when an approval or a question waits on you, blue when there is only an unread message. **Manager** takes you back to the chat or list you left in that browser tab, and the tab's title names the manager you have open. The command palette also lists **Manager**, **New manager**, and each manager by name.

Choose **Workspace → Approvals** in the Manager sidebar to review pending approval cards from all managers, grouped by manager. You can also open `/manager/approvals` directly. The count includes pending approvals; questions have their own page, **Questions**. The page stays available when there are no pending approvals. **Open chat** jumps to that manager’s waiting cards. On a phone, open the menu to reach **Approvals**.

After you decide, the card stays visible while the action runs and shows its final result, including a refusal. Choose **Clear results** to remove completed cards from the view. If the result could not be loaded, **Retry result** reads it again without repeating your decision.

## How to use it

1. Open **Manager**. With no manager yet, Cezar shows **Set up your first manager**.
2. Describe the job in **What should this manager do?**, or pick a preset: **Watch my repositories**, **Keep PRs moving**, or **Run big tasks**.
3. Choose the projects, manager agent, model, account, and agent for new tasks, then select **Create**.

Your text becomes the manager's standing instructions and its first message, so it starts working right away. Each manager gets its own character in the sidebar. To change its character, name or instructions later, open the gear and select **Persona…**.

Type `/` in the chat for commands:

| Command | What it does |
| --- | --- |
| `/status` | Gives a short status of the connected projects. |
| `/attention` | Lists what needs you now. |
| `/tasks` | Lists running and recently finished tasks. |
| `/prs` | Lists open pull requests and what each one waits for. |
| `/check` | Runs a watch check now. |
| `/stop` | Stops the current turn. |

The manager handles one turn at a time. Messages you send during a turn run next, folded into one turn. A manager runs only for a turn, so an idle chat costs nothing and survives a restart. A turn that runs for 30 minutes without finishing is stopped with an error, so a stuck agent never holds the chat.

If a turn fails, the chat says what happened and what to do, for example *Sign in to Claude Code again* or *Usage limit reached until 14:00*, with **Try again** to send your message again. A passing failure, such as a dropped connection or busy servers, is retried once after a short pause before you see anything, and a conversation the agent can no longer resume restarts fresh with a recap. A turn that already ran a command is never retried, so nothing runs twice.

If a turn hits a provider usage limit and the provider gives a reset time, the chat shows when the manager resumes instead of an error. Until then, the manager runs no watch checks or jobs. When the limit resets, it sends your message again, and any job the limit stopped runs again. A message you send before then runs right away, together with the waiting one. **Don't resume**, or `/stop`, cancels the replay. Turning off **Auto-resume after a usage limit** in Settings → Resources makes a usage limit show as a normal error again.

On a desktop, Enter sends and Shift+Enter starts a new line.

The prompt sits above the attachment and send controls in one rounded composer. Open the settings gear in the chat's top bar and select **Manager agent**. The dialog groups the agent, account, model and effort choices, with a separate section for agents allowed to start new tasks. Changes save as you choose. The composer has no **Options** button, configuration pickers or status row beneath it; **Stop** stays inside the composer while the Manager works. Manager chat and setup have no dictation control.

### On a phone

A phone opens on Manager when you load the cockpit's address with nothing after it, in a browser tab or from the home screen. Tablets and desktops keep returning to your last page, and so does a server with Manager off or a first run that isn't finished. Links keep working as they are, and **Tasks** in the menu takes you to your last project page.

With one manager you land in its chat. With several you get the list: a card per manager with its device, status, latest message and what waits on you, managers holding an approval first. Search filters by manager or device name, and **Needs you** keeps only the managers waiting on you. Once installed on your home screen, a bar at the bottom gives you **Manager**, **Tasks** and **More**, which opens the menu. It hides while you type and inside a task.

Below tablet width the chat keeps to one header row, with back, the manager's name and the gear. The arrow opens the list of managers, where the menu button is. The projects picker moves into the gear.

On a phone, the keyboard's return key starts a new line and only **Send** sends. With a hardware keyboard attached to a phone or tablet, ⌘+Enter or Ctrl+Enter sends. This applies to task threads too.

On a phone, Refresh lives in the gear menu, and a spinner beside the manager's name shows while it works.

### Prompt buttons

**Prompt buttons…** in the gear menu holds up to six buttons of your own, each a short label and the prompt it sends. They sit above the composer while the draft is empty and nothing waits on you, and a tap sends that prompt right away. A prompt that spells a `/` command, such as `/check`, runs that command. A manager has none until you add some, and with none there is no button row at all. Prompt buttons belong to the manager, like its jobs, because a manager spans projects.

The desktop's **Watching** panel is a sheet on a phone and a narrow window: the tasks the manager started come first, then the projects it watches, its last check and its jobs. Open it from the list icon beside the gear or, once a reply has started tasks, the **Tasks** chip above the composer. **Close**, a downward drag on its header, Back, or the edge swipe on iOS closes it. On a phone it opens at medium height and grows when larger text or the keyboard needs the room; on a wider screen it is a centered dialog. **View all tasks** stays pinned at the bottom. Opening a task or **View all tasks** replaces the sheet in your history, so going back returns to the chat with the sheet closed.

The tasks list shows the most recent few. **View all (N)** below it opens the global Tasks table filtered to every task the manager started or follows, across its projects, as a **Started by** facet you can share by URL or clear like any other. Archived ones are behind the table's **Archived** view.

In the CezarBot app the phone navigation holds at every size, an iPad included: the bottom bar replaces the sidebar, **More** opens what the sidebar held, and inside a manager **Tasks** opens the tasks it started, with their count. A task thread keeps the bottom bar too: a task opened from a manager keeps **Manager** highlighted, a tap goes back to that chat where you left it, and another tap opens the managers list. A desktop browser keeps the sidebar.

## Connect repositories

A manager starts with **All projects**, which covers every project registered in Cezar, including projects you add later. To limit it, open the projects picker under the manager's name, or in the gear on a phone, and select individual projects. The chat records each change, for example *Connected to api, web*.

Cezar refuses any `cez-manager` command that targets a project the manager is not connected to. An approval also fails if you disconnected its project after the manager proposed it.

## Refresh

**Refresh** sets how often a manager checks its connected projects. The default is 15 minutes. Change it in the top-bar settings gear: **Off**, 5, 15, or 30 minutes, 1 or 4 hours, or 1 day.

A check reads the task stores and the same GitHub data the GitHub tab uses, then looks for attention items:

| Source | Attention item |
| --- | --- |
| Tasks | A task, including a dispatched subtask, waits on you: a question, a gate, a finished turn, a budget stop, or worktree scripts that need a recovery action. |
| Tasks | A task failed in the last 7 days, or reached review, and you have not opened it since. |
| Tasks | A running task has shown no activity for two hours. This includes a task in a project this Cezar has not opened: a manager reads it as running or waiting on you, as it really is, never as failed. |
| Pull requests | A pull request that is not a draft has a conflict or failing checks, is ready to merge, or waits on a review. |
| Automations | An enabled automation's newest log line is an error. |

**A quiet check costs nothing.** With no new attention item, Cezar makes no model call and leaves no message. A new item starts one model turn. The manager then tells you what deserves your attention, or decides that nothing does and stays silent. You pay for that turn in both cases.

The manager's instructions decide what a check raises. A manager whose instructions are about something else, such as reviewing your own work, mentions only what serves them and stays silent about unrelated pull requests and failed tasks. A manager with no instructions raises every attention item. To widen or narrow what a manager watches, change its instructions in **Persona…**.

Cezar reports each item once. The same task failing again is a new item, and so is a pull request problem that cleared and came back.

**Check now** in the gear menu and `/check` skip that gate, so they always run a model turn. When nothing needs you, the chat shows *Checked: nothing needs you right now.*

> **Good to know**:
>
> - Checks run while Cezar runs. Checks missed while it was closed collapse into one.
> - After a failed check, the interval doubles, up to 16 times the Refresh setting. A failed check stays out of the chat: the cause goes to the cockpit log and the manager's `state.json`. After three failed checks in a row, the chat shows one line saying what to do, for example *Background checks keep failing. Sign in to Claude Code again…*, and keeps that one line for the whole run of failures.
> - Connected projects with no GitHub access still get task checks.

## Jobs

A job is a saved prompt the manager runs on its own interval, for example a morning summary of open pull requests. Open the gear, select **Jobs…**, then add a name, a prompt, and an interval from 5 to 10,080 minutes. You can also ask the manager in chat to add one, and it proposes the job as a card you approve. A manager holds up to 32 jobs.

Replies from a job carry a *Job:* label with its name in the chat. Jobs ignore the attention gate and keep running with **Refresh** set to **Off**, so **every due job spends a model turn**. Use the switch in **Jobs…** to pause a job.

## Task updates

A manager hears about its tasks as soon as they change, without waiting for the next refresh. When a task it started finishes, fails, is cancelled or waits on you, Cezar posts a *Task update* to the chat within seconds, without a model turn: the task card, its state, and for a finished task its last message. A long message shows its first lines, and **Show the whole message** opens the rest. A failed task and a task that waits on you are important, so they raise a notification unless you turned **Notify me when important** off.

Then the manager takes one turn of its own to act on the result. It summarizes what matters, follows up with the task, starts the next one, or proposes what needs your approval. When a task waits on you with questions or for your approval, the manager asks them on a question card, and it passes your answers back to the task. Updates that arrive within a couple of seconds of each other share one turn, and the turn waits while the manager is answering you. If you write first, that reply covers the update and no extra turn runs.

A dispatched task tree reports once, when its root settles, plus any subtask that waits on you. Tasks you start yourself report nothing unless the manager follows them. Ask it to keep an eye on one, and it runs `cez-manager task follow <run>`, or `task unfollow` to stop.

**Each follow-up is a model turn you pay for.** To keep the cards and skip the turns, turn off **Follow up on its tasks** in the gear menu. The manager then reads the updates with your next message. A cancelled task, and a failed one that resumes on its own after a usage limit, never start a turn. **Refresh** does not affect updates: with Refresh set to **Off**, the cards and follow-ups still come.

> **Good to know**: A task update is posted once, also across restarts. A task that changed while Cezar was closed reports when Cezar starts again, and the next refresh does not report the same change.

## Automation results

An automation the manager creates reports to it. Each time one of its runs finishes, Cezar posts the task's last message to the chat word for word, with a card that opens the task, within seconds and without a model turn. The message carries an *Automation:* label with the automation's name and an unread dot. A failed run is posted as an important message: one short line with the reason, such as an expired login or a usage limit, plus the task card, and it raises a notification. Each run is posted once, also across restarts, and a later refresh does not report the same run again.

The new automation still starts paused, and you enable it from its approval card. Open the automation's page to see which manager it reports to. Under **Reports to**, pick **Every result**, **Failures only** or **Nothing**, or select **Unlink**. An automation you made yourself can report to a manager from the same card.

From the command line, `cez automation add … --report-to-manager --manager <id> [--report-mode post-result|failure-only|none]` links a new automation, and `cez automation report <id> --mode <mode>` or `--unlink` changes an existing one. `cez automation show <id>` and `cez automation list --json` include the link. A manager links what it creates to itself unless it passes `--no-report`.

> **Good to know**: Automations that don't report to a manager behave as before. When you delete a manager, its automations drop the link on their next run.

## Deactivate a manager

Deactivating a manager stops its work without deleting it. Its chat, memory, jobs, settings and automation links stay as they are. Open the gear and select **Deactivate…**, or right-click the manager in the sidebar. The dialog lists what stops and what keeps going. To switch every manager off at once, for example before a laptop sleeps, open the **⋯** menu next to *Managers* in the sidebar and select **Deactivate all…**. **Settings → Manager** has the same controls.

While a manager is inactive:

- It makes **no model calls**. Checks, jobs and follow-up turns stop, and so do its notifications. **Check now** is off.
- Tasks it started keep running, and their *Task update* cards still post to its chat. The manager hears those updates on its next turn after you reactivate it.
- Automations that report to it keep running and keep posting their results.
- You can still decide its approvals. Its questions stay listed with a *Manager inactive* label but leave the Questions count. **Dismiss** closes a question without reactivating the manager. Answering a question needs the manager, so the cockpit asks you to reactivate it first.
- Its avatar turns grey with a pause badge, and it moves below the active managers under *Inactive*.

You can still type in the chat of an inactive manager. **Reactivate and send** asks you to confirm, then reactivates it and sends your message.

To bring a manager back, select **Reactivate…** in the chat banner, the gear or the sidebar menu. Reactivating spends nothing by default: checks and jobs restart from that moment, so overdue ones don't all run at once. The chat shows one line that counts what happened while the manager was off. Tick **Catch me up** to run one check right away. That check is one model turn.

## What a manager can do

| Action | Chat and job turns | Watch checks |
| --- | --- | --- |
| Read tasks, pull requests, workflows, and automations | Does it | Does it |
| Start a task, with a workflow or Dispatch | Does it | Refused |
| Message a running task, or continue a finished one | Does it | Refused |
| Cancel a task it started, with everything that task dispatched | Does it | Refused |
| Retry a failed or cancelled task | Does it | Refused |
| Create or edit an automation, which always leaves it paused | Does it | Refused |
| Add a job | Proposes it | Refused |
| Remove a job | Does it | Refused |
| Merge a pull request | Proposes it | Refused |
| Enable an automation | Proposes it | Refused |

A watch check reads text that anyone can write in a pull request, so Cezar keeps it read-only. It can ask you to act, and you then ask for the action in chat.

Merging, enabling an automation and adding a job happen only when you approve. The manager puts a card in the chat with its reason. **Reject** acts at once. **Approve** opens a summary of what will happen, as a sheet on a phone and a dialog on a desktop, and you confirm there. The manager learns the outcome on its next turn.

The summary shows the project, pull request, title, method, head commit and a link for a merge, the name, revision and definition for an automation, and the name, interval and full prompt for a job. On the card, a job's prompt and an automation's definition stop at three lines. Select **Show all** to read the rest. If Cezar refuses a decision, the reason appears on the card.

When a card is out of view, an **N approvals waiting** pill sits above the composer. Select it to jump to the oldest one, even if it is further back than the loaded messages.

To skip the summary, open **Settings → Manager**, pick the manager, and turn off **Merges**, **Automations**, **Jobs** or **Connector calls**. All four are on by default, each manager keeps its own choice, and it applies to every device on that server. With a switch off, **Approve** sends the decision straight away. The card still appears and still needs your tap, so a manager never acts on its own.

**Dismiss** closes a card without deciding, for a proposal that no longer applies. A merge card whose pull request was already merged or closed is dismissed on its own: as soon as cezar sees the pull request merged or closed (its chip on the card, the merge box, an automation poll), when you open the chat, at the manager's next watch check, or when you approve it.

A merge card also lists the tasks behind its pull request, the one that opened it first, then tasks that review or mention it, up to three plus a count. Select one to open that task.

Approving a merge goes through the same merge route as the GitHub tab, with the method the manager proposed or the repository's default. The card is tied to the commit you were shown. If someone pushes after the proposal, the merge fails instead of landing code you never saw. An automation card shows the definition and is tied to it the same way, so an edit after the proposal fails too.

## Connectors

A connector is an MCP server your Claude session already has: a claude.ai connector such as Gmail, Google Calendar or Google Drive, or an MCP server from your own Claude config. Every connector starts at **Off**, so a manager cannot use one until you grant it. Open the manager's gear menu and select **Connectors…** to see them; select **Refresh** when the list is empty or out of date.

Give each connector one of three levels:

| Level | What the manager can do |
| --- | --- |
| Off | Nothing. Every tool is denied. |
| Read | Calls the connector's read tools directly. |
| Read+write | Calls read tools directly, and proposes each write tool for your approval. |

Cezar classifies a tool by its name. A tool that starts with a read verb such as `get_`, `list_`, `search_`, `read_` or `find_` is a read tool, and every other tool is a write tool. A tool with an unfamiliar name counts as a write tool.

You can override a single tool with **deny**, **ask**, or **allow without asking**. **ask** puts the call on an approval card, and **allow without asking** lets the manager call the tool directly. Use **allow without asking** on a write tool only when you trust every call the manager can make with it.

A write produces an approval card, like a merge. The card shows the connector, the tool and the exact arguments. When you approve, Cezar runs that call and nothing else: it checks the arguments against what you approved and refuses any difference, so the manager cannot change a recipient or a message body afterward. The result appears in the chat and reaches the manager on its next turn.

> **Good to know**:
>
> - A grant applies from the manager's next turn, and so does a revoke. A card that waits when you revoke its tool fails on approval.
> - Only Claude managers can use connectors. Other agents have their own MCP configuration.
> - Watch checks never get connector tools, because they read text anyone can write.
> - A manager with no connector granted does not load any, so their tool lists never take up its context. The Connectors dialog looks them up when you open it.
> - Connectors disconnect and reconnect on their own. When one is down, the manager tells you it is temporarily unavailable, and a write card for it fails with the same message.
> - Cezar does not pass connector grants to tasks the manager starts.

## Memory and sessions

A manager does not keep one endless conversation. A chat continues the same session only while it is active: within 55 minutes of the last turn, under 100,000 tokens of context, and less than 12 hours after the session started. Otherwise the next turn starts a new session. Scheduled checks and jobs always start a new one. Your chat stays one thread; only what the model carries changes.

A new session starts from:

- **Memory**: what you asked the manager to remember, such as "open full PRs, not drafts" or "HTML design before UI work".
- The open question cards, the notes since its last turn, and the tasks it follows with their status.
- The last few messages between you and the manager.

The manager can read older messages with `cez-manager history` and a task's details with `cez-manager task`.

Open the manager's gear menu and select **Memory…** to see, edit, add or delete entries. The manager saves an entry when you tell it something it should keep. Memory holds at most 40 entries and 6 KB. A Claude manager's earlier Claude Code memory is imported once, and Claude Code's own memory is then switched off for it, so there is one memory, the same on every agent.

> **Good to know**: Memory is for lasting preferences and decisions, not task results. Tasks keep their own reports, and the manager looks them up when it needs them.

## Agents, accounts, model and cancelling

Open the chat's settings gear → **Manager agent** to change the manager's agent, account, model and effort in one dialog. The account field lists accounts for the selected agent. Changing agents clears the previous model and account. **Use workspace default** follows your workspace's account setting; **Default** explicitly selects the agent's discovered account. During setup, **Model and effort** also offers agent and account choices.

> **Good to know**: A manager's shell is limited to `cez-manager` and read-only `gh` commands. Claude Code enforces that with a hook. On Codex, the manager runs in Codex's isolated read-only mode and cezar runs each command itself, only after the same check, so Codex needs 0.169.0 or newer. A Codex manager cannot write files and cannot use connectors. Its `gh` commands run directly on your machine, outside any Claude Code Bash sandbox, and `CEZ_CODEX_NETWORK=0` blocks them (user-allowed `gh` patterns included) while `cez-manager` keeps working.

Use **Agent for new tasks** during setup or in the dialog's **For new tasks** section to check the agent accounts available for tasks the manager starts. You can select several, including two Claude accounts and one Codex account. The manager chooses from those pairs for each new task; requests for an unselected runner or account are refused. Your choices stay saved for later messages. The manager itself keeps its own agent and account.

**Automatic** clears the account selection and lets the manager choose an agent and account for each task, including when you ask it to use a particular one. If the manager makes no choice, the task uses the manager's own agent. For example, a Claude Code manager's task runs on Claude Code even when the project's default is Codex. Existing tasks keep their agent. A workflow with agents selected for individual steps keeps those step choices.

When the manager names no account, the task takes your selection as its default: the first selected account with usage capacity. An account waiting out a usage limit is skipped for the next one, and the task's timeline records which account was picked and why, for example "claude Work out of limits until …, used claude Home". If every selected account is out of limits, the task waits in the queue and starts when the first one resets. The manager is told in the command's output. A task that reaches a usage limit while it works moves to another selected account with capacity, keeping the same task, history and branch. This works even when Settings → Agents → Automatic fallback is off, and the task never moves to an account you did not select. `cez-manager status` lists the selected accounts and which are out of limits.

> **Good to know**: Mid-task moves follow the same rules as automatic fallback. A graph workflow, or a step with more steps after it, waits for the reset instead.

The manager can still name an account with `cez-manager task create --runner claude --account <id>`. If that account is out of limits, the output warns and names a selected account with capacity. The task records the requested account and the account that actually ran; open its agent badge to see the account label. If a selected account was deleted, task creation is refused instead of using another account.

A manager can pick the model and reasoning effort of a task it starts, for example `cez-manager task create --model opus --effort max`, and of a finished task it continues with `task say`. Cezar checks the choice against the task's agent and the models it discovered on this machine. An unknown model, another agent's model, or an effort the model lacks is refused with the valid choices, instead of quietly running on the default. `cez-manager task <run>` and `tasks --json` show each task's agent, model and effort.

`cez-manager task cancel <run> --reason "…"` stops a task and every task it dispatched. They become **cancelled**, the task thread shows who cancelled it and why, and the worktree and branch stay for you to inspect. A manager may cancel only the tasks it started. To let it cancel other tasks in its write repositories, yours included, turn on **Cancel any task** in its settings menu. A read-only repository never allows it.

`cez-manager task retry <run>` starts a failed or cancelled task again as a new task, with the same objective, workflow, model and effort. With **Automatic**, it keeps the original agent. A selected **Agent for new tasks** also applies to retries; an incompatible model or effort is refused.

Tasks you start yourself also appear in the manager's task list and attention, marked as started by the user, and each task lists the pull request it opened. So a manager can see work that already exists before it starts more. `cez-manager workflows` marks what each workflow can do (push, open a pull request, post to GitHub, or read-only), and the manager is told to use a read-only workflow when you ask only for a review.

> **Good to know**: Every `cez-manager` command takes `--help`, and `task create --help` lists the project's workflows. A mistyped subcommand such as `task foo` fails with the valid ones instead of being read as a task id.

## Send screenshots and files

Paste a screenshot, drop a file on the chat, or select **+** in the composer, including on the setup screen. The manager sees images directly and gets every file as a path it can read, then and in later messages. Deleting a manager deletes its attachments.

## File long text with a task

Paste a transcript, notes or a log into the chat and ask the manager to file it or pass it to a task. The manager never retypes the text. It names your message, and Cezar copies it into the task word for word on the server, with the files you attached. The task's objective holds the manager's instruction, then your message between two marker lines.

A manager does this with `--attach-last-user-message` on `cez-manager task create` or `task say`, or `--from-message <id>` for an earlier message. For text it wrote itself, it saves a file under `files/` in its working folder and passes `--file`. Claude managers may write only in that folder, and `--file` reads only from it or the manager's attachments.

Cezar refuses a task or message whose text is a placeholder such as `[transcript here]`, `PASTE` or `<<<…>>>` where content belongs, and the manager tells you so in its reply.

> **Good to know**: Claude refuses any shell command longer than about 10,000 characters, even one its allow list matches. That is why long text reaches a task through the server, not through a command.

## Answer a manager's questions

When a manager needs a decision from you, it shows a question card with clickable choices, its recommended choice first. Every question also offers **Other…** and **Need more info**. Once answered from the card, it collapses to each question with your answer. A reply you type in the chat shows as your own message and leaves open cards open, marked **May be out of date**; the manager closes them on its next turn if your reply covered them.

A card closes on its own when a newer card asks the same thing again (the same card name, or every one of its questions), when the manager withdraws it, or when the pull request or task it declares it is about is finished. A closed card shrinks to one line that says why. To answer every open question in one place, see [Questions](#questions).

## Questions

Choose **Workspace → Questions** in the Manager sidebar, or open `/manager/questions`, to see every open question from your managers and tasks in one list, grouped by where it was asked. Answer it there, **Dismiss** it (the agent is told you skipped it; **Undo** is offered for a few seconds), or use **Open in context** to jump to the card in its chat. A manager card that relays a task's question appears once, under the task, and answering either copy closes both. A card you answer or dismiss there stays in place for 30 seconds with what happened (your answer and where it was sent, or **Dismissed**), then leaves; so does one that closes while you are looking at it, with the reason. It leaves only once you are idle (not while the pointer or keyboard focus is in the list, nor for 3 seconds after you scroll or press a key), and the text you are reading does not move. The count drops as soon as you click.

The count beside **Questions** includes only questions that still need you. A card marked **May be out of date** still counts until you dismiss it or the agent closes it. A question left unanswered for longer than the **Move to Older after** setting (7 days by default) moves to **Older** and stops counting; it is not closed. **Closed** lists the last seven days with the reason each closed. With managers turned off, **Questions** sits in the project sidebar and lists task questions.

## Now in Manager mode

**Workspace → Now** in the Manager sidebar, and the **Now** tab on a phone, open the managers' own Now (`/manager/now`). It stays in Manager mode; a project's **Now** is unchanged. It lists what every manager needs from you: their questions, approvals and important messages, and the tasks they started or follow. A task row names its manager. To see one manager, pick it in the **All managers** menu at the top right, or tap the floating filter button on a phone; **Show all managers**, or the button's **×**, goes back. Rows work as in a project's Now: answer or approve in place, **✕** to dismiss with **Undo**, **⋯** for more, and **Probably done** for what no longer needs you. The badge on **Now** counts these items.

## Choose read-only or write access

Each repository a manager connects to has its own access, which you set in the projects picker. **All projects** sets it for everything the manager reaches, and a project's own setting overrides that. New managers have write access.

On a read-only repository, the manager still sees its tasks and pull requests, and can start tasks that answer questions. Cezar keeps those tasks read-only with each agent's own read-only mode: they can't change files, have no GitHub login or git credentials, so can't push or open pull requests, and get none of the project's private MCP servers. Kimi, omp and Antigravity have no read-only mode, so a read-only task won't start on them; pick another agent. The manager can message only these tasks there, not your own Ask tasks. The manager can't dispatch, merge, enable or set up automations there, and an approval card already waiting fails once you lower access. Tasks already running keep the access they started with.

## Notifications

Everything a manager writes appears in its chat with an unread dot. When it judges something important, such as a task blocked on you or a big task finishing, it also raises a system notification. So does any approval or question card. On your own Mac, Windows or Linux machine this is the operating system's notification and needs no open tab. On a hosted Cezar it is a browser notification, which you turn on in Settings. If you are reading that chat, Cezar does not notify you.

Selecting a browser notification brings the cockpit forward and opens that manager's chat.

To silence a manager, open the gear and turn off **Notify me when important**.

## The notch on a Mac

In the desktop app on macOS, managers that are working or need you appear around the camera at the top of the screen. On a Mac without a notch they float at the top centre of the screen.

- The main pill shows one manager and what it is doing. A manager that needs you comes first.
- A second pill appears when more than one manager is active, with up to four small faces and a count of the rest.
- Hover over the main pill or click it to open the list, then click a manager to open its chat.
- Click a small face to open that manager's chat, or the count to open the list.

Approvals stay in the chat. Nothing shows while no manager is active. Turn it off in **Settings → Notifications → Manager notch**.

## Open a task from a card

Every task the manager names or starts appears as a card in the chat. A card shows the task's title, live status, and added and removed lines. Dispatched tasks appear as their root task, and you can ask the manager about the subtasks.

Select a card to open that task's own thread and keep working there. The task then shows a `Back to <manager>` link, which stays for the browser session as you move between the task's tabs. A pull request chip opens the pull request in the GitHub tab.

Pull requests and issues become chips in replies, question cards and on the Questions page when the manager names the project: a `[[pr:…]]` marker, a GitHub link, or a connected project's id or name followed by `/` or `#` and the number (`frontends/2902`). A bare `#12` resolves to the project a marker in the same reply or card names, else to the only connected project, and a number with no `#` and no project stays plain text. Card headers are always plain text.

## Tool limits by agent

Cezar gives a manager `Read`, `Grep`, `Glob`, and a `Bash` allowlist of `cez-manager` plus read-only `gh` commands. **Only Claude enforces those limits.** Choose Claude for a manager that reads pull requests from people you do not trust.

| Agent | What limits the manager |
| --- | --- |
| Claude | The agent CLI denies every tool and command outside the list, and any command over about 10,000 characters. A hook checks every `Bash` call against Cezar's read-only policy (below). Writing is allowed only under the manager's own `files/` folder, never during a watch check. |
| Pi | Pi has no per-command allowlist, so Cezar removes `Bash`. The manager can read files but cannot run `cez-manager`, so it has no tasks, proposals, or status commands. |
| Every other agent | In a chat or a job, the system prompt is the only limit. These agents ignore the tool list and can run any command the agent allows. A watch check, which reads pull requests nobody vetted, runs in the agent's read-only mode instead, with no `gh` login. It works from the snapshot Cezar puts in its prompt. Kimi, omp, and Antigravity have no read-only mode, so their watch checks keep the full shell. |

On every agent, Cezar's own routes still refuse what they should: out-of-scope projects, actions during a watch check, and a `cez-manager` merge without your approval. Those rules guard `cez-manager` only. An agent that ignores its prompt can still call `gh pr merge` directly, because nothing on that agent blocks the command.

### What a Claude manager can run

A Claude manager's `Bash` call runs only when it is one of these commands:

- `cez-manager …`, whose server enforces every approval.
- `gh pr view|list|diff|checks|status`, `gh issue view|list`, `gh run view|list`, `gh release view|list`, `gh repo view` and `gh search code|commits|issues|prs|repos`, without `--web`, with `--repo` only as `OWNER/REPO`, with no URL or host path to a server other than github.com, and with no `--jq` filter that reads the environment or files.
- `gh api <path>` as a GET: `-X GET`, `--paginate`, `--jq`, `--template`, `--cache` and `Accept` or `X-GitHub-Api-Version` headers only. `-f`, `-F`, `--field`, `--input`, any other method, `graphql`, `--hostname` and full URLs are refused.
- Any of those piped into `jq`, `grep`, `head`, `tail`, `wc`, `sort`, `uniq` or `cut`, which read the pipe only: no file arguments, and no jq filter that reads the environment or files.
- A `gh <group> <verb>` pattern you allowed in the manager's **Shell access** settings (below).

Always refused, even if you allow a pattern: `gh pr merge|review|comment|edit|close|ready`, `gh issue comment|edit|close`, `gh workflow run`, `gh run rerun`, `git push` and every `gh api` write. Also refused: `;`, `&&`, `||`, `&`, `$(…)`, backticks, `$VAR`, redirects, subshells, loops, globs, unquoted newlines, and a pipe into any other program, such as `sh` or `xargs`. Newlines inside quotes are fine, so a long multi-line objective passes as one argument, and so does a `cez-manager … --stdin <<'EOF'` heredoc with a quoted delimiter, which expands nothing. A `cez-manager` command the policy still cannot read falls back to Claude's own `cez-manager` allow rule. Where the hook cannot run (on Windows), only the fixed `cez-manager` and `gh` prefixes are allowed, with no `gh api` and no pipes.

The manager's system prompt lists exactly these rules: Cezar builds that part of the prompt from the same tables the hook checks.

### Shell access

Open the manager's settings menu and choose **Shell access** to see the commands it was refused lately, with the reason for each. When a refused command is a read-only `gh <group> <verb>` (`view`, `list`, `status`, `diff` or `checks`), the row offers **Allow … (read-only)**: one click lets the manager run that pattern from its next turn, with the same `--web`, `--repo`, host and `--jq` checks as the built-in reads. Only gh's own command groups qualify: a write, a `gh auth`, `config`, `secret` or `variable` command, a gh extension or alias, and anything that is not `gh` cannot be allowed. Remove a pattern or clear the log from the same dialog.

> **Good to know**:
>
> - Managers are available by default, and nothing runs until you create one. The default 15-minute Refresh then spends tokens only when a check finds a new item.
> - `CEZ_MANAGERS=0` turns managers off. It removes the Manager mode and Settings → Manager, stops the timers, and makes the API answer `409`. Cezar reads it at boot, only the exact value `0` opts out, and your managers stay in `~/.cezar/` for when you turn the feature back on.
> - Definitions live in `~/.cezar/managers.json` and chats in `~/.cezar/managers/`. Deleting a manager removes its chat and jobs. Tasks it started stay where they are.
> - The effort picker applies to Claude only.
> - With usage telemetry turned on, Cezar counts how Manager mode is used (entering it, creating a manager, sending a message, deciding a proposal) with fixed labels only. It never sends a manager's name, instructions, messages, or projects. See `docs/telemetry.md` for the full list. With telemetry off, nothing is sent.
> - Managers have no autonomous merges and no per-manager budget.
> - A read-only task drops the project's private MCP servers, not the MCP servers in your own agent config (for example `~/.codex/config.toml`). Keep tools that can write out of your user-level agent config if a manager's read-only tasks must stay read-only.
