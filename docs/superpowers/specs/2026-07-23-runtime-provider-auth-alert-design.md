# Runtime Provider Authentication Alert

**Date:** 2026-07-23
**Status:** Approved

## Problem

cezar immediately marks a provider disconnected when a running agent reports an authoritative
authentication rejection. The existing global banner, however, disappears whenever any other
provider remains connected. A revoked Claude Code token can therefore turn the Claude badge red
without producing any persistent notification outside Settings.

The alert must remain visible across routes, name every affected provider, link directly to the
provider settings, and be dismissible. Dismissal must survive a reload without changing the
provider's actual connection state. A later authentication incident must surface again.

## Goals

- Show a persistent, workspace-wide alert for runtime authentication failures even when another
  provider is connected.
- List every provider with a current, undismissed runtime-authentication incident.
- Let the user dismiss the incidents currently shown, with dismissal surviving reloads and project
  switches.
- Resurface the alert after a provider recovers and later encounters a new runtime-authentication
  failure.
- Keep raw vendor errors, credentials, and account identity behind the server boundary.

## Non-goals

- Dismissal does not reconnect a provider, clear its runtime failure latch, or enable task controls.
- This does not add a general-purpose notification center or notification API.
- Ordinary disconnected or not-installed providers do not become runtime-authentication incidents.
- Dismissal need not disappear simultaneously from other already-open browser tabs. The persisted
  workspace state becomes authoritative when those tabs next reload or refetch it.

## Provider Status Contract

`ProviderStatus` gains one optional field:

```ts
interface ProviderStatus {
  provider: ProviderId
  status: ProviderConnectionState
  hint?: string
  authFailureId?: string
}
```

`authFailureId` is an opaque, non-secret UUID generated by cezar. It is present only while the
provider is latched as disconnected because of a runtime authentication rejection. Normal probe
results never contain it. The browser accepts the field only when it is a bounded, non-empty
string; malformed values cannot become notification text or dismissal keys.

`ProviderAuthService` creates the identifier when an unlatched provider first reports a runtime
authentication failure and retains the same identifier for that incident. Duplicate normalized
events and ordinary status polls retain the identifier rather than creating new incidents.
Successful explicit **Check again** recovery clears the latch and identifier. If the provider is
later rejected again, the service creates a different identifier, including after a cezar process
restart.

The identifier is generated independently of vendor output. It discloses neither credential
material nor the raw runtime error.

## Dismissal State

Workspace UI state gains a bounded optional map:

```ts
interface WorkspaceUiState {
  dismissedProviderAuthFailures?: Partial<Record<ProviderId, string>>
}
```

Each value is the last incident ID dismissed for that provider. There are only three fixed
provider keys, and the server validates both keys and bounded string values. The map lives in
`~/.cezar/ui-state.json`, so it follows the user across projects and survives reloads. Its absence
is the zero-configuration default and means no incident has been dismissed.

An incident is visible when its provider status contains `authFailureId` and the stored dismissal
for that provider does not equal that identifier. Stale dismissal entries are harmless: a new
identifier no longer matches and automatically resurfaces the alert.

Clicking dismiss captures every incident currently rendered and shallow-merges those
provider-to-identifier pairs with the latest workspace UI-state cache. The client optimistically
hides them, sends the complete dismissal map through the existing workspace UI-state PUT, and
reconciles with the merged response. If persistence fails, the client restores server truth and
shows a danger toast. A failure that arrives after the click is not accidentally dismissed because
its identifier was not part of the captured set.

## Banner Behavior

`ProviderBanner` remains the single app-shell banner component and applies this precedence:

1. If one or more undismissed runtime incidents exist, render the runtime-authentication alert.
2. Otherwise, if no provider is connected, render the existing generic missing/unknown-provider
   banner.
3. Otherwise render nothing.

The runtime alert appears even when another provider is connected. It lists affected providers in
the stable catalog order: Claude Code, Codex, OpenCode. Suggested copy:

> Provider authentication failed during a task: Claude Code, OpenCode.

The alert includes:

- a project-aware link to `/settings/agents#providers`;
- a keyboard-accessible dismiss button with an explicit accessible label;
- an assertive, non-modal live-region role suitable for a newly arrived authentication failure;
- the existing compact placement above the route scroller on desktop and mobile.

Dismissing the runtime alert never modifies provider status. If no provider is connected, the
existing non-dismissible “No agent provider is connected” safety banner becomes visible after the
runtime alert is dismissed. If another provider is connected, dismissal leaves no banner.

## Data Flow

```text
runtime 401
    |
    v
ProviderAuthService latch + opaque authFailureId
    |
    +--> provider-status SSE row --> provider query cache
    |
    +--> GET /api/providers/status --> authoritative reload/reconcile
                                      |
                                      v
                     ProviderBanner compares current incidents
                     with workspace UI-state dismissals
                                      |
                       dismiss ------+------> PUT workspace UI state
```

The existing 30-second provider polling, reconnect reconciliation, and explicit **Check again**
behavior remain unchanged. The runtime incident field simply rides the existing status response
and SSE row.

## Error Handling and Compatibility

- Older clients ignore the additive `authFailureId` field.
- Older stored UI-state files omit the dismissal map and continue to parse.
- Malformed status rows or dismissal maps fail closed and do not render raw values.
- A workspace UI-state read failure leaves incidents undismissed, which is the safer visible
  fallback.
- A workspace UI-state write failure restores the banner and reports the failure through the
  existing toaster.
- `/api/health` remains unchanged.
- No credential files, keychains, or vendor network calls are added.
- `CEZ_DRY_RUN=1` continues to report connected providers and ignores runtime failure reports.

## Verification

- Core tests prove incident IDs are stable across duplicate reports and ordinary polls, clear only
  after successful explicit recovery, and differ for a later incident.
- API type-contract tests cover the optional field without weakening provider-row validation.
- Server/SSE tests prove runtime invalidation emits only the provider, disconnected state, safe
  hint, and opaque incident ID.
- Workspace UI-state tests cover the bounded dismissal map and passthrough round-tripping.
- Component tests cover one and multiple affected providers, stable display order, visibility while
  another provider is connected, dismissal persistence, write rollback, keyboard access, and
  generic-banner precedence.
- Browser verification starts a task against the real revoked Claude credential, observes the
  immediate app-wide alert, follows its Settings link, dismisses it, reloads, and confirms Claude
  remains disconnected without the dismissed runtime alert.

## Alternatives Rejected

### Client-only hint parsing and `localStorage`

This is smaller, but it couples behavior to human-readable hint text and cannot reliably identify
a distinct later incident. A tab that missed the SSE event also has no explicit incident identity.

### Dedicated notification API

A notification resource with list and dismiss endpoints would be general, but it adds server
lifecycle and persistence machinery that this single alert type does not need. Provider status and
the existing workspace UI-state route already provide the required boundaries.
